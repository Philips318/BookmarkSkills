# 构思框架参考

选择性地使用这些框架。挑选适合这个想法的视角，不要机械地运行每个框架。目标是打开思考，而不是遵循清单。

## SCAMPER

通过应用七种不同操作来改造现有想法的一种结构化方法：

- **Substitute：** 可以替换哪个组件、材料或流程？如果替换核心技术会怎样？目标受众？商业模式？
- **Combine：** 如果把它和另一个产品、服务或想法合并会怎样？哪两个通常不放在一起的东西能创造新东西？
- **Adapt：** 还有什么类似这个？可以借鉴其他行业、领域或时代的哪些想法？自然界中有什么平行现象？
- **Modify (Magnify/Minimize)：** 如果把它放大 10 倍会怎样？缩小 10 倍呢？如果夸大某个特性？如果把它剥离到绝对最小？
- **Put to other uses：** 还有谁可以使用它？它还能解决什么问题？如果把它用于完全不同的上下文会发生什么？
- **Eliminate：** 如果完全移除某个功能会怎样？零配置版本是什么样？步骤减半会是什么样？
- **Reverse/Rearrange：** 如果按相反顺序执行步骤会怎样？如果由用户来完成系统的工作（或反过来）？如果反转价值链？

**最适合：** 改进或重新想象现有产品/功能。对 greenfield 想法帮助较小。

## How Might We (HMW)

使用 “How Might We...” 格式把问题重构为机会：

- 从观察或痛点开始
- 将其重构为 “How might we [desired outcome] for [specific user] without [key constraint]?”
- 为同一个问题生成多个 HMW framing，不同 framing 会打开不同解决方案

**好的 HMW 特质：**
- 足够窄，可以行动（“...help new users find relevant content in their first 5 minutes”）
- 足够宽，可以容纳创造性解决方案（不是“...add a recommendation sidebar”）
- 包含能迫使创造力出现的张力或约束

**差的 HMW 特质：**
- 太宽：“How might we make users happy?”
- 太窄：“How might we add a button to the settings page?”
- 内嵌解决方案：“How might we build a chatbot for support?”

**最适合：** 重新框定卡住的思考。当某人锚定在解决方案上时，把他们拉回问题。

## First Principles Thinking

把想法拆解到基本真理，然后从那里重建：

1. **我们知道什么是真的？**（不是假设，不是惯例，而是实际为真）
2. **我们在假设什么？** 列出每个假设，即使那些看起来显而易见
3. **哪些假设可以挑战？** 对每个假设问：“这真的是物理定律，还是只是过去一直这样做？”
4. **从真理重建。** 如果只有基本真理，你会构建什么？

**最适合：** 跳出渐进式思维。当每个想法都像是对现状的小改进时。

## Jobs to Be Done (JTBD)

关注用户试图完成什么，而不是他们说自己想要什么：

- **Functional job：** 他们试图完成什么任务？
- **Emotional job：** 他们希望感觉如何？
- **Social job：** 他们希望别人如何看待自己？

格式："When I [situation], I want to [motivation], so I can [expected outcome]."

**关键洞察：** 人们不是购买产品，而是雇用产品完成一项工作。竞争产品并不总在同一类别中。（Netflix 与睡眠竞争，不只是与其他流媒体服务竞争。）

**最适合：** 理解真正的问题。当你不确定自己是否在解决正确问题时。

## Constraint-Based Ideation

有意施加约束以迫使创造性解决方案出现：

- **时间约束：** “如果你只有 1 天来构建它会怎样？”
- **功能约束：** “如果它只能有一个功能会怎样？”
- **技术约束：** “如果你不能使用 [the obvious technology] 会怎样？”
- **成本约束：** “如果它必须永远免费会怎样？”
- **受众约束：** “如果你的用户从未用过电脑会怎样？”
- **规模约束：** “如果它需要服务 10 亿用户会怎样？如果只服务 10 个呢？”

**最适合：** 穿透复杂性。当想法变得太大或太模糊时。

## Pre-mortem

想象这个想法已经失败。反向推演：

1. 现在是 12 个月后。项目发布并失败了。出了什么问题？
2. 列出每个合理的失败原因，包括技术、市场、团队、时机
3. 对每种失败模式：这可以预防吗？这是否说明想法需要改变？
4. 你愿意接受哪些失败模式？哪些会杀死项目？

**最适合：** 阶段 2 评估。压力测试那些感觉不错但尚未被检验的想法。

## Analogous Inspiration

看看其他领域如何解决类似问题：

- 哪个行业已经解决了这个问题的某种版本？
- 如果 [specific company/product] 来构建，它会是什么样？
- 哪个自然系统以这种方式运行？
- 有什么历史先例？

关键是找到*结构性*相似，而不是表面相似。“Uber for X” 是表面相似。“一个解决陌生人之间信任问题的双边 marketplace” 是结构相似。

**最适合：** 阶段 1 发散。生成与显而易见方法真正不同的变体。
