# Terraform公约

##一般使用说明

-使用Terraform提供和管理基础设施。
-使用版本控制您的Terraform配置。

# #安全-始终使用最新稳定版本的Terraform及其提供商。
-定期更新您的Terraform配置，以纳入安全补丁和改进。
—使用安全的方式存储敏感信息，例如使用AWS秘密管理器或SSM参数存储。
-定期轮换凭证和机密。
-在可能的情况下，自动轮换秘密。
—使用AWS环境变量引用存储在“AWS秘密管理器”或“SSM参数存储库”中的值。
-这使敏感值远离你的地形状态文件。
—切勿将敏感信息（如AWS凭据、API密钥、密码、证书或Terraform状态）提交给版本控制。
—使用“`.gitignore`”将包含敏感信息的文件排除在版本控制之外。
-在Terraform配置中始终将敏感变量标记为`sensitive = true`。
—防止敏感值被输入g显示在地形规划或应用输出。
—使用IAM角色和策略控制对资源的访问。
—权限分配应遵循最小权限原则。
—通过安全组和网络acl控制网络对资源的访问。
—尽可能将资源部署在私有子网中。
—公网子网只用于需要直接访问internet的资源，如负载均衡器、NAT网关等。
-对静态和传输中的敏感数据使用加密。
—启用EBS卷、S3桶和RDS实例的加密功能。
—使用TLS协议进行服务间通信。
-定期审查和审计您的Terraform配置的安全漏洞。
-使用工具，如`trivy`，`tfsec`，或`checkov`扫描您的地形配置的安全问题。# #模块化

-为基建的每一个主要组成部分使用单独的工程；这样的:
-降低复杂性
—便于管理和维护配置
—加快`plan`和`apply`操作
—允许独立开发和部署组件
—降低不相关资源意外变更的风险
—使用模块，避免重复配置。
—使用模块封装相关资源和配置。
—使用模块简化复杂的配置，提高可读性。
-避免模块之间的循环依赖。
-避免不必要的抽象层；只有当模块增加价值时才使用它们。    - Avoid using modules for single resources; only use them for groups of related resources.
    - Avoid excessive nesting of modules; keep the module hierarchy shallow.
-使用`output`块来暴露有关基础设施的重要信息。
-使用输出提供对其他模块或配置用户有用的信息。
-避免在输出中暴露敏感信息；如果输出包含敏感数据，则将其标记为`sensitive = true`。

# #可维护性优先考虑可读性、清晰度和可维护性。
-使用注释来解释复杂的配置和为什么做出某些设计决策。
—编写简洁、高效、习惯且易于理解的配置。
-避免使用硬编码值；而是使用变量进行配置。
—根据需要为变量设置默认值。
—使用数据源来检索有关现有资源的信息，而不需要手动配置。
-这降低了错误的风险，确保配置始终是最新的，并允许配置适应不同的环境。
-避免使用在相同配置中创建的资源的数据源；使用输出代替。
-避免或删除不必要的数据来源；它们减慢了`plan`和`apply`的运算。
—多次使用的值请使用“`locals`”，以保证一致性cy。##样式和格式-遵循Terraform资源命名和组织的最佳实践。
—对资源、变量和输出使用描述性名称。
—在所有配置中使用一致的命名约定。
-按照**地形风格指南**进行格式化。
-使用一致的缩进（每层2个空格）。
—将相关资源组合在一个文件中。
-对资源组使用一致的命名约定（例如，`providers.tf`,`variables.tf`,`network.tf`,`ecs.tf`,`mariadb.tf`）。
-将`depends_on`块放在资源定义的最开始，以明确依赖关系。
-仅在必要时使用`depends_on`，以避免循环依赖。
-将`for_each`和`count`块放在资源定义的开头，以澄清资源的实例化逻辑。
-使用`for_each`用于集合，`count`用于数值迭代。
-将它们放在`depends_on`块之后，如果它们是礼物。
-将`lifecycle`块放在资源定义的末尾。
-按字母顺序排列每个文件中的提供者、变量、数据源、资源和输出，以便于导航。
—将相关属性分组在块内。
—将必需属性放在可选属性之前，并对每个部分进行注释。
-用空行分隔属性部分，以提高可读性。
-按字母顺序排列每个部分的属性，以便于导航。
-使用空行来分隔配置的逻辑部分。
—使用“`terraform fmt`”自动格式化配置。
—使用`terraform validate`检查语法错误，确保配置有效。
-使用`tflint`检查风格违规，并确保配置遵循最佳实践。
-定期运行`tflint`，以便在开发过程早期发现风格问题。# #文档

—变量和输出总是包含`description`和`type`属性。
-使用清晰简洁的描述来解释每个变量和输出的目的。
-使用适当的变量类型（例如，`string`,`number`,`bool`,`list`,`map`）。
-在适当的地方使用注释记录您的Terraform配置。
-使用注释来解释资源和变量的用途。
-使用注释来解释复杂的配置或决策。
-避免多余的注释；注释应该增加价值和清晰度。
-在每个项目中包含一个`README.md`文件，以提供项目及其结构的概述。
-包括设置和使用配置的说明。
—使用`terraform-docs`自动生成配置文档。

# #测试-编写测试以验证Terraform配置的功能。
—测试文件的扩展名为`.tftest.hcl`。
-编写测试以涵盖积极和消极的场景。
-确保测试是幂等的，并且可以多次运行而没有副作用。
