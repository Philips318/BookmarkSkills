# Dart和Flutter

Dart和Flutter团队推荐的最佳实践。这些说明摘自[Effective Dart]（https://dart.dev/effective-dart）和[架构建议]（https://docs.flutter.dev/app-architecture/recommendations）。

##有效镖

在过去的几年中，我们编写了大量的Dart代码，并了解了哪些代码运行良好，哪些代码不运行良好。我们与您分享这些内容，以便您也可以编写一致、健壮、快速的代码。主要有两个主题：

1.  * *是一致的。**当涉及到格式和大小写等问题时，关于哪个更好的争论是主观的，无法解决的。我们所知道的是，保持“一致”客观上是有帮助的。    If two pieces of code look different it should be because they *are* different in some meaningful way. When a bit of code stands out and catches your eye, it should do so for a useful reason.
2.  * *是短暂的。** Dart被设计为熟悉的，因此它继承了许多与C、Java、JavaScript和其他语言相同的语句和表达式。但我们创建Dart是因为这些语言提供的功能还有很大的改进空间。我们增加了一堆功能，从字符串插值到初始化形式，以帮助您更简单，更容易地表达您的意图。    If there are multiple ways to say something, you should generally pick the most concise one. This is not to say you should `code golf` yourself into cramming a whole program into a single line. The goal is code that is *economical*, not *dense*.
主题

为了便于理解，我们将指南分成几个单独的主题：

** *样式** -这定义了布局和组织代码的规则，或者至少是`dart format`不能为您处理的部分。样式主题还指定了标识符的格式：`camelCase`、`using_underscores`等。

** *文档** -它告诉你所有你需要知道的关于注释内部的内容。文档注释和常规的、普通的代码注释。

** *用法-教你如何充分利用语言特性来实现行为。如果它在一个语句或表达式中，它在这里被覆盖。

** *设计** -这是最软的话题，但也是最广泛的话题。它涵盖了我们所学到的关于为库设计一致、可用的api的知识。如果它在类型签名或声明中，则会进行遍历。

如何阅读主题每个主题都被分成几个部分。章节包含指导方针的列表。每条指导原则都以以下其中一个词开头：

** *DO**准则描述了应该始终遵循的做法。几乎永远不会有正当的理由偏离它们。

** *不要**准则是相反的：事情几乎从来都不是一个好主意。希望我们不像其他语言那样有那么多这样的错误，因为我们没有那么多的历史包袱。

** *PREFER**准则是你*应该*遵循的做法。然而，在某些情况下，这样做是有意义的。只要确保你理解忽略指导原则的全部含义。

** *AVOID**准则是“偏好”的双重：你不应该做的事情，但在极少数情况下可能有充分的理由去做。** *考虑**准则是你可能想或不想遵循的做法，这取决于情况、先例和你自己的偏好。

一些准则描述了不适用该规则的例外情况。在列出这些例外情况时，可能并不详尽—您可能仍然需要对其他情况使用您的判断。

这听起来就像如果你没有系好鞋带，警察就会来敲你的门。事情没那么糟。这里的大多数指导方针都是常识，我们都是通情达理的人。一如既往，我们的目标是编写漂亮、易读和可维护的代码。

*像单词一样，首字母缩略词和长度超过两个字母的缩写要大写。

##扑动架构建议

本页介绍了体系结构最佳实践，为什么它们很重要，以及
我们是否推荐它们用于您的Flutter应用程序。
你应该把这些建议当成建议，
没有坚定的规则，你应该这么做
根据你的应用的独特需求调整它们。本页上的最佳实践具有优先级，
这反映了Flutter团队对它的强烈推荐。

** *强烈建议：**您应该始终执行此建议，如果
您开始构建一个新的应用程序。你应该强烈考虑
重构一个现有的应用来实现这个实践，除非这样做
与你目前的方法发生根本冲突。
** *推荐**：这种做法可能会改善你的应用。
** *条件**：这种做法可以在某些情况下改善你的应用程序。

关注点分离

你应该把你的应用分成UI层和数据层。在这些层中，您应该进一步按职责将逻辑划分为类。

####使用定义清晰的数据和UI层。
* *强烈推荐* *关注点分离是最重要的架构原则。
数据层向应用程序的其余部分公开应用程序数据，并包含应用程序中的大部分业务逻辑。
UI层显示应用程序数据并监听来自用户的用户事件。UI层包含用于UI逻辑和小部件的独立类。

####在数据层使用存储库模式。
* *强烈推荐* *

存储库模式是一种软件设计模式，它将数据访问逻辑与应用程序的其余部分隔离开来。
它在应用程序的业务逻辑和底层数据存储机制（数据库、api、文件系统等）之间创建一个抽象层。
在实践中，这意味着创建Repository类和Service类。

####在UI层使用ViewModels和Views。(MVVM)
* *强烈推荐* *关注点分离是最重要的架构原则。
这种特殊的分离使您的代码更不容易出错，因为您的小部件仍然是“哑的”。

####使用`ChangeNotifiers`和`Listenables`处理小部件更新。
* *条件* *

b>处理状态管理有很多选择，最终取决于个人喜好。`ChangeNotifier`API是Flutter SDK的一部分，是一种方便的方法，可以让您的小部件观察ViewModels中的变化。

####不要在小部件中添加逻辑。
* *强烈推荐* *逻辑应该封装在ViewModel的方法中。视图应该包含的唯一逻辑是：
*简单的if语句显示和隐藏基于一个标志或空字段在ViewModel小部件
*动画逻辑依赖于小部件来计算
*布局逻辑基于设备信息，如屏幕大小或方向。
*简单的路由逻辑

####使用域层。
* *条件* *

>用于具有复杂逻辑需求的应用程序。

只有当你的应用程序有非常复杂的逻辑，拥挤了你的视图模型时，才需要域层。
或者如果你发现自己在ViewModels中重复逻辑。
在非常大的应用中，用例是有用的，但在大多数应用中，它们增加了不必要的开销。

处理数据

小心处理数据可以使代码更容易理解，更少出错，并且
防止创建格式错误或意外的数据。####使用单向数据流。
* *强烈推荐* *

数据更新应该只从数据层流向UI层。
UI层中的交互被发送到数据层，在那里它们被处理。

####使用`Commands`处理来自用户交互的事件。
* *推荐* *

命令可以防止应用程序中的渲染错误，并标准化UI层向数据层发送事件的方式。

####使用不可变数据模型。
* *强烈推荐* *

不可变数据对于确保任何必要的更改只发生在适当的位置（通常是数据层或域层）至关重要。
由于不可变对象在创建后不能修改，因此必须创建一个新实例来反映更改。
这个过程可以防止UI层中的意外更新，并支持清晰的单向数据流。

####使用freeze或built_value来生成不可变的数据模型。
* *推荐* *可以使用包在数据模型`freezed`或`built_value`中帮助生成有用的功能。
这些可以生成常见的模型方法，如JSONser/des、深度相等性检查和复制方法。
如果您有很多模型，这些代码生成包可能会给您的应用程序增加大量构建时间。

####创建单独的API模型和域模型。
* *条件* *

b>用于大型应用程序。

使用单独的模型增加了冗长性，但避免了ViewModels和用例中的复杂性。

###应用结构

组织良好的代码既有利于应用本身的健康发展，也有利于编写代码的团队。

####使用依赖注入。
* *强烈推荐* *

依赖注入可以防止应用程序拥有全局可访问的对象，从而降低代码出错的几率。
我们建议您使用`provider`包来处理依赖注入。####使用`go_router`进行导航。
* *推荐* *

Go_router是编写90%的Flutter应用程序的首选方式。
有一些特定的用例是go_router无法解决的，
在这种情况下，您可以直接使用`Flutter Navigator API`，或者尝试在`pub.dev`上找到的其他包。

####对类、文件和目录使用标准化的命名约定。
* *推荐* *

我们建议根据它们所代表的体系结构组件来命名类。
例如，您可能有以下类：

* HomeViewModel
*主屏幕
* UserRepository
* ClientApiService

为了清晰起见，我们不建议使用可能与Flutter SDK中的对象混淆的名称。
例如，您应该将共享的小部件放在名为`ui/core/`的目录中，
而不是名为`/widgets`的目录。

####使用抽象存储库类
* *强烈推荐* *存储库类是应用中所有数据的真实来源，
并促进与外部api的通信。
创建抽象存储库类允许您创建不同的实现，
它可以用于不同的应用程序环境，例如“开发”和“登台”。
