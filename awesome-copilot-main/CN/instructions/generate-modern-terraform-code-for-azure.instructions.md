# # 1。使用最新的地形和供应商
始终以最新稳定的Terraform版本和Azure提供商为目标。在代码中，指定所需的Terraform和提供程序版本来执行此操作。保持提供程序版本更新，以获得新特性和修复程序。

# # 2。清晰地组织代码
用逻辑文件分离构造地形配置：

—资源使用“`main.tf`”
—输入使用`variables.tf`—输出使用`outputs.tf`-遵循一致的命名约定和格式（`terraform fmt`）

这使得代码易于导航和维护。

# # 3。封装在模块中

使用Terraform模块对可重用的基础设施组件进行分组。对于将在多个上下文中使用的任何资源集：

-创建一个模块与自己的variables/outputs-引用它而不是复制代码
-这促进了重用和一致性

# # 4。利用变量和输出- **使用带有类型和描述的变量参数化所有可配置值
- **为可选变量提供默认值**
- **使用输出**公开关键资源属性，供其他模块或用户参考
- **标记敏感值**以保护机密

# # 5。提供商选择（AzureRM vs AzAPI）

**在大多数情况下使用`azurerm`provider** -它提供了高稳定性并覆盖了大多数Azure服务
**使用`azapi`提供程序**仅在您需要的情况下：
-最新的Azure功能
-`azurerm`中尚未支持的资源
在代码注释中记录选择**
-如果需要，两个提供者可以一起使用，但在有疑问时首选`azurerm`# # 6。最小的依赖关系- **未经确认，不得在项目范围之外引入**其他供应商或模块
-如果需要特殊的提供程序（如`random`，`tls`）或外部模块：
-添加注释来解释
—确认用户批准
—保持基础设施堆栈精简，避免不必要的复杂性

# # 7。确保幂等性

—写入可重复应用且产生相同结果的配置
- **避免非幂等行为**：
-在每个应用程序上运行的脚本
-如果创建两次可能会冲突的资源
**测试通过做多个`terraform apply`运行**，并确保第二次运行的结果是零变化
-使用资源生命周期设置或条件表达式来优雅地处理漂移或外部更改

# # 8。状态管理- **使用远程后端**（如带有状态锁定的Azure Storage）来安全地存储Terraform状态
-促进团队协作
- **永远不要提交状态文件**到源代码控制
—防止冲突，保持基础设施状态一致

# # 9。文件及图表

**保持最新的文件**
- **更新README.md**与任何新的变量，输出，或使用指令每当代码的变化
-考虑使用`terraform-docs`等工具实现自动化
- **更新架构图**以反映每次重大更新后基础架构的变化
-文档完备的代码和图表确保整个团队理解基础架构

# # 10。验证和测试变更- **运行`terraform validate`**，在应用更改前检查`terraform plan`输出
-尽早捕获错误或意外修改
- **考虑实施自动检查**：
- CI管道
-预提交钩子
-强制格式化、检查和基本验证
