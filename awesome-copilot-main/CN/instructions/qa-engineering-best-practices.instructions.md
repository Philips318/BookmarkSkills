# QA工程最佳实践GitHub Copilot的结构化指令集，用于协助质量保证工程任务，包括测试设计、自动化和跨任何技术堆栈的缺陷管理。

---

核心测试原则**尽早测试，经常测试**：把测试移到左边——在代码旁边写测试，而不是在代码后面。
- **一次测试一件事**：每个测试用例应该验证一个行为或断言。
测试是一级代码：对测试代码应用与产品代码相同的可读性、命名和重构标准。
**快速失败**：测试应该产生明确的、可操作的失败，直接指向错误的行为。
- **确定性测试**：测试必须在每次运行时产生相同的结果。消除随机性、时间依赖性和共享可变状态。
- **独立测试**：任何测试都不应依赖于另一个测试的副作用。测试必须以任何顺序运行。

##测试金字塔

按照测试金字塔来平衡覆盖率、速度和维护成本：

|层|范围|数量|速度||-------|-------|----------|-------|
|单位|单一功能/类别|许多（60 - 70%）|毫秒|
|集成|模块边界，DB， API契约|中等（20 - 30%）|秒|
|端到端|用户全程UI +后端|很少（5 - 10%）|分钟|

-更喜欢对业务逻辑和边缘情况进行单元测试。
-使用集成测试来验证服务和外部依赖之间的契约。
-为关键用户路径和烟雾套件保留端到端测试。

测试命名约定

始终使用**Given / When / Then** (GWT)或**should_doX_whenY**模式。```
// Good – describes scenario, action, expected result
test('should return 404 when product id does not exist')
test('given an expired token, when the user calls /me, then it returns 401')

// Bad – vague, implementation-focused
test('test1')
test('check user')
```
—将相关测试分组在以待测单元命名的`describe`/`context`块中。
-个别情况使用`it`或`test`。
-测试名称必须作为独立的句子可读。

---

断言最佳实践

- **每次测试一个逻辑断言**在实际情况下；避免断言多个不相关的事情。
-使用**特定匹配器**超过相等性检查（`toContain`,`toBeGreaterThan`,`toMatchObject`）。
-总是断言**精确的期望值**，而不仅仅是真实性（`expect(result).toBe(42)`而不是`expect(result).toBeTruthy()`）。
—对于异常测试，断言异常类型和消息。
-在测试快乐路径时，更喜欢正面断言而不是负面断言。```typescript
// Good
expect(response.status).toBe(200);
expect(response.body.items).toHaveLength(3);

// Avoid
expect(response).toBeTruthy();
expect(response.body).not.toBeNull();
```

测试数据管理

-使用**工厂或构建器**创建测试数据-避免在每次测试中硬编码原始对象。
-保持测试数据最少：只包括与测试相关的字段。
-每个测试运行使用**唯一标识符**，以避免在共享环境中发生冲突。
-绝不在测试中使用生产数据或PII。
-重置或隔离测试之间的状态（内存DB、回滚事务、模拟依赖关系）。

##嘲讽和存根准则

-在边界**处模拟** （HTTP客户端，DB适配器，消息队列）-不深入业务逻辑。
-对于纯函数和简单的值对象，更倾向于真正的实现。
-存根返回受控数据；mock还可以验证交互—选择正确的工具。
—在测试之间重置所有模拟以防止状态泄漏。
-如果原因不明显，说明为什么依赖被嘲笑。

---## API测试

-验证每个端点的**状态码**、**响应模式**、**报头**和**响应时间**。
-测试所有**HTTP方法**的端点暴露（GET， POST， PUT， PATCH， DELETE）。
-覆盖认证和授权路径：有效令牌，过期令牌，缺失令牌，错误的角色。
-测试**边界值**输入：空字符串，null，最大长度，特殊字符，Unicode。
-验证**错误响应体**遵循一致的模式。
-对PUT和DELETE操作断言**幂等。

---

UI /端到端测试-目标是用户可见的行为，而不是实现细节（避免断言CSS类或内部状态）。
-使用**可访问选择器**按优先顺序：`role`→`label`→`test-id`→`text`。
-避免`sleep`/固定等待；使用显式等待元素状态（可见，启用，网络空闲）。
-针对**稳定、隔离的环境**运行端到端测试（非共享暂存）。
-保持E2E场景**短而集中** -将长流程分解为较小的可组合步骤。
-捕获屏幕截图和跟踪故障，以便于调试。

---

性能测试-在编写性能测试之前定义slo（服务水平目标）：目标延迟p50/p95/p99、吞吐量、错误率。
-在负载测试中包括**上升阶段，**稳态阶段和**下降阶段。
-在**实际数据量下进行测试** -使用空db的合成测试不具有代表性。
跟踪结果随着时间的推移，以检测**性能退化**。
-区分**负载测试**（预期流量）、**压力测试**（超出容量）和**浸泡测试**（随时间持续负载）。

Bug报告标准

一份好的bug报告包括：1. **标题**：简明，具体-包括成分，作用和症状（`[Checkout] Order total is incorrect when coupon is applied`）。
2. **环境**：操作系统、browser/runtime版本、部署环境。
3. **步骤复制**：编号，最小，确定性。
4. **预期结果**：应该发生的事情。
5. **实际结果**：实际发生的情况，包括错误消息和堆栈跟踪。
6. **严重性**：严重/高/中/低（根据业务影响定义）。
7. **附件**：截图、日志、网络跟踪、测试id。

---

测试覆盖指南

-以有意义的覆盖率为目标，而不是一个百分比目标——对于琐碎的测试，100%的行覆盖率是毫无价值的。
-优先覆盖**关键路径**，**复杂逻辑**和**以前的bug区域**。
-跟踪**分支覆盖**和**突变得分**旁边的行覆盖。
-使用覆盖率报告寻找未测试的边缘案例，而不是游戏参数。

---集成

—在任何合并到main/trunk之前，测试必须在CI中通过—没有异常。
-在每次提交时运行**快速测试**（单元，lint）；在PR合并或夜间运行**慢测试**（集成，端到端）。
-在CI输出中显示测试失败，包括测试名称，故障原因和相关日志。
-存档测试报告和工件（JUnit XML，覆盖HTML，跟踪）作为CI构建工件。
—配置**片状测试检测**：自动重试一次，重复不一致后标记为片状。

##测试评审清单

在批准变更测试的PR之前：-[]新行为在适当的金字塔级别上由测试覆盖。
—[]测试名称清晰，并遵循项目约定。
—[]无`sleep`、`Thread.Sleep`或任意超时。
- [] mock在每次测试后重置。
-[]没有硬编码的特定于环境的值（url，凭据）。
-[]测试是独立的，可以单独运行。
—[]测试代码是可读的，不需要阅读实现。
