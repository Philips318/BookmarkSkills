#代码空间和Devcontainer效率

只有当任务涉及到`.devcontainer/`、代码空间大小、预构建或工作空间成本时，才加载此引用。

如果回购是第一次导入代码空间，首先定义一个最小基线，然后进行优化。

##审计命令

按此顺序检查：

1. 查看`.devcontainer/`是否存在。
2. 如果不存在，则首先收集基线需求：language/toolchain、所需的cli、预期的启动目标、机器大小约束，以及是否需要预构建。
3. 回顾`.devcontainer/devcontainer.json`。
4. 确保`.devcontainer/devcontainer-lock.json`存在；如果没有，建议添加它，因为许多repos早于锁定文件支持。
5. 查看相关的Dockerfiles、特性和设置脚本。
6. 查看推荐机器大小、预构建或启动期望的文档。

对于新设置（第2步），在使用数据证明它们是合理的之前，尽量少启动并避免使用可选工具。

##常见废物来源-超大的基础图像
—不必要的包或扩展
-缓慢的创建后引导步骤
-为太多分支启用了预构建
-缺少关于机器尺寸或闲置超时的指导

优先修复顺序

1. 删除不必要的包、特性和扩展
2. 减少启动命令和创建后安装
3. 建议保持吞吐量的最小机器大小
4. 将预构建范围缩小到持续使用的分支（默认分支，活动发布分支，以及每周超过5个代码空间的任何分支）
5. 增加或加强空闲超时和清理指导

##安全更改规则-不要通过移除团队每天实际需要的工具来优化启动。
—将repo更改与org或用户设置区分开来。
-当有效控制存在于回购之外时，更喜欢文档。
避免将devcontainer变成类似于生产环境的镜像，除非团队明确需要这样做。

##报告重点

当报告代码空间改进时，分开：

-更快的启动
-降低稳态工作空间成本
-较低的预构建花费
-仍然需要组织或用户行动的仅用于指导的建议
