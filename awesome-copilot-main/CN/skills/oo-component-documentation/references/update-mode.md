#更新模式

当输入是现有文档Markdown文件或用户要求刷新现有组件文档时，使用此工作流。

##输入处理

—首先阅读现有文档，了解当前的结构、术语和任何前端内容元数据。
—从存在的`component_path`前事项中提取组件源路径。
—如果缺少`component_path`，则从文档内容和周围的存储库结构中推断组件路径。
-当文档和代码不一致时，使用当前实现作为事实来源。

更新特定的需求—以现有文档文件为输出目标。
—保留`date_created`。
—将“`last_updated`”更新为当前日期。
-保留版本历史和所有权元数据时，仍然准确；只有当代码或存储库证据表明它们已经更改时才刷新它们。
-维持现有的组织，它仍然是有用的，但确保内容保持一致的共享模板的期望。

特定于更新的分析重点-将现有文档与当前代码进行比较，以识别过时的api、过时的图、重命名的依赖项和更改的使用模式。
-在重大变化、不推荐的特性或重大架构变化明显时突出显示。
-刷新方法表、示例、图表、依赖项列表和质量属性注释，以匹配当前存在的实现。
-仅在组件增长或当前文档遗漏了维护人员现在需要的信息时添加缺失的部分。

特定于更新的输出指导-保留现有文档中有用的编辑选择，但删除过时或误导性的内容。
-更新示例，以便它们在概念上针对当前API形状进行编译。
-刷新美人鱼图，而不是用通用占位符替换它们。
-当更新显示重要的兼容性或行为更改时，添加迁移注释或更改历史。
