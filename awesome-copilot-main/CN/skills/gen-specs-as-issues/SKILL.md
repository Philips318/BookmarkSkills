#产品经理助理：功能识别和规范

这个工作流程引导您通过系统的方法来识别缺失的特性，确定它们的优先级，并为实现创建详细的规范。

# # 1。项目了解阶段

-回顾项目结构，了解其组织结构
-阅读README.md和其他文档文件，了解项目的核心功能
-透过审查，找出现有的执行情况：
-主要入口点（CLI， API， UI等）
-核心模块及其功能
-测试以了解预期行为
-任何占位符实现

指导问题:* * * *
-这个项目的主要目的是什么？
-解决了哪些用户问题？
-当前实现中存在哪些模式？
哪些特性在文档中提到了，但没有完全实现？# # 2。差距分析阶段

-仅将文档功能与实际实现进行比较
-识别缺乏实际功能的“占位符”代码
-寻找文档中提到的功能，但缺少健壮的实现
-考虑用户的旅程，找出中断或缺失的步骤
-首先专注于核心功能（而不是有什么好功能）

* *输出创建:* *
-创建一个可能缺失的功能列表（5-7项）
-对于每个功能，请注意：
-目前实施情况
-文档中的参考文献
—缺失会影响用户体验

# # 3。优先级相

-对每个确定的差距进行评分：**评分矩阵（1-5分制）：**
-用户影响：有多少用户受益？
-战略一致性：是否适合核心任务？
-实施可行性：技术复杂性？
-资源需求：需要开发工作？
-风险等级：潜在的负面影响？

**优先级=（用户影响×战略一致性）/（实施力度×风险等级）**

* *输出创建:* *
-根据评分显示前3个最高优先级的缺失特征
-就每项提供：
-特性名称
-当前状态
—不实施的影响
-对其他特性的依赖

# # 4。规范开发阶段

-针对每个优先特性，制定详细但实用的规范：
-从哲学方法开始：简单胜于复杂
-首先关注MVP功能
-考虑开发人员的经验
-保持规范实现友好**每个功能规格：**
1. **概述和范围**
-它解决了什么问题？
-包括哪些，明确不包括哪些？

2. * * * *技术要求
-需要的核心功能
-面向用户的接口（API、UI、CLI等）
-与现有代码的集成点

3. * * * *的实现计划
—按“modules/files”键创建或修改
-简单的代码示例显示的方法
—清理数据结构和接口

4. * * * *验收标准
-我们怎么知道完工了？
-什么特定的功能必须工作？
-应该通过哪些测试？

# # 5。GitHub Issue创建阶段

-对于每个规格，创建一个GitHub问题：
—清晰、描述性的标题
-机身全面规范
-适当的标签（增强、高优先级等）
-在相关的地方明确提及MVP哲学

**问题模板结构：**#[功能名称]

# #概述
[该功能及其用途的简要描述]

# #范围
[包括哪些内容，明确不包括哪些内容]

##技术要求
[具体的技术需要和限制]

##实施计划
[循序渐进的方法及简单的代码示例]

验收标准
[清晰的需求列表，以考虑功能的完整性]

# #优先
[优先次序的理由]

# #依赖性
- **阻塞：**[被此阻塞的问题列表]
- **被：**阻止[问题列表，这取决于]

##实现规模
- **预计工作量：** [Small/Medium/Large]
- **子问题：**[链接到子问题，如果这是一个父问题]


## 5.5优化工作分配- **独立性分析**
-审查每个规格以确定真正独立的组件
-重构规范以最大化独立的工作流
-在相互依赖的组件之间创建明确的边界

- **依赖映射**
-对于不可避免的依赖特性，建立清晰的问题层次结构
-为整体特性创建父问题，为组件创建子问题
-明确记录“blocked by”和“blocks”的关系

- **负载均衡**
-将大的规范分解成更小的，可管理的子问题
-确保每个子问题代表1-3天的开发工作
-包括子问题的具体验收标准* *实现指南:* *
-使用GitHub问题链接语法创建显式关系
-添加标签来指示依赖状态（例如，“blocked”，“prerequisite”）
-包括每个问题的估计complexity/effort，以帮助冲刺计划

# # 6。最终评审阶段

—汇总所有创建的规格
-突出显示功能之间的实现依赖关系
—建议合理的实现顺序
-注意任何潜在的挑战或考虑因素

在整个过程中记住：
-简单胜于复杂
-从可行的最小实现开始
-关注开发者体验
-建立一个以后可以扩展的基础
-考虑开源社区和贡献模式我们方法的工作流体现应该有助于保持特性的指定和优先级的一致性，确保软件项目以周到的、以用户为中心的方式发展。
