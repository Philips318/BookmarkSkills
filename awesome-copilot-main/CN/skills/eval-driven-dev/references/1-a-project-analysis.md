#步骤1a：项目分析

在查看代码结构、入口点或编写任何工具之前，请先了解该软件在现实世界中的作用。此分析是后续每一步的基础——它决定优先考虑哪些入口点、定义哪些eval标准、使用哪些跟踪输入以及构建哪些数据集条目。

---

调查什么

阅读项目的README、文档和顶级源文件。你在寻找五个问题的答案：

# # # 1。这个软件是做什么的？

写一段简明扼要的摘要。它解决了什么问题？成功的运行是什么样的？

# # # 2。谁在使用它，为什么？目标用户是谁？主要用例是什么？这个方法解决了哪些其他方法解决不了的问题？这有助于你理解这个应用程序的“质量”意味着什么——一个与客户聊天的聊天机器人与一个综合多源报告的研究代理有着不同的质量要求。

# # # 3。库存能力

列出应用程序提供的独特功能、模式或特性。要具体。例如:

-用于抓取库：单页抓取，多页抓取，基于搜索的抓取，语音输出，脚本生成
-对于语音座席：问候，FAQ处理，查询，转人，呼叫摘要
-研究代理：主题研究，多源综合，引文生成，报告格式化每个功能可能需要自己的入口点、自己的跟踪和自己的数据集条目。这个列表直接提供给步骤1c（用例）和步骤4（数据集多样性）。

# # # 4。什么是现实的输入？

描述应用程序处理的真实输入-而不是玩具样例：

-对于网页刮板：“带有导航、广告、动态内容、表格、嵌套结构的杂乱HTML页面-通常为5KB-500KB的HTML”
-研究代理：“需要多源合成的开放式研究问题，有3-10个子问题”
-语音代理：“有背景噪音、中断和模糊请求的多回合对话”具体说明**规模**（多大）、**复杂性** (messy/diverse)和**多样性**（何种类型）。这直接提供了跟踪输入选择（步骤2）——如果你没有在这里描述真实的输入，你最终会使用绕过应用程序实际逻辑的玩具输入。

**本节是操作约束，而不仅仅是文档。**步骤2c（跟踪输入）和4c（数据集条目）将交叉引用这些特征，以验证跟踪输入和数据集条目与现实世界的规模和复杂性相匹配。具体和量化——写“5KB-500KB的HTML页面”，而不是“各种HTML页面”。

# # # 5。困难的问题/失效模式是什么？

是什么让这个应用程序的工作变得困难？它在实践中失败的地方是什么？这些成为最有价值的评估场景：对于刮板：“畸形的HTML，动态js渲染的内容，复杂的嵌套模式，超过上下文窗口的非常大的页面。”
-研究代理人：“矛盾的来源，需要多步骤推理的问题，幻觉引用”
-对于语音代理：“不明确的呼叫者意图，账户查找失败，同时调用工具”

每个故障模式应该映射到至少一个评估标准（步骤1c）和至少一个数据集条目（步骤4）。

质量检查

在继续之前，请验证：

-“这个软件做什么”部分用非技术用户可以理解的术语描述了应用程序的目的-不仅仅是“它运行一个图表”或“它调用OpenAI”。
-功能清单列出了至少3个功能（如果项目有的话）-如果你只找到了1个，你可能只查看了代码库的一部分
-真实的输入特性描述真实世界的规模和复杂性，而不是最简单的可能输入
-失败模式是特定于这个应用程序的域，而不是通用的（“错误的输入”不是失败模式，“带有未关闭标签的格式错误的HTML破坏了解析器”是）

在项目中应该忽略什么项目可能包含属于它自己的development/test基础结构的目录和文件——`tests/`、`fixtures/`、`examples/`、`mock_server/`、`docs/`、演示脚本等。它们是为项目开发人员而存在的，而不是为您的eval管道而存在的。

**关键**：不要使用项目的测试fixture，模拟服务器，示例数据或单元测试基础设施作为eval跟踪或数据集条目的输入。它们是为开发速度和隔离性而设计的——小的、干净的、确定的数据，可以绕过现实世界的每一个困难。使用它们会产生非常简单的评估，无法捕捉到真正的质量问题。

当您在分析过程中遇到这些目录时，请注意它们的存在，但将它们视为项目的实现细节——而不是QA管道的数据源。你的QA管道必须针对现实环境测试应用，而不是针对项目自己的测试捷径。
