#步骤1c：评估标准

根据项目分析（`00-project-analysis.md`）和你已经记录的入口点（`01-entry-point.md`），定义这个应用程序的质量维度。

本文件有两个用途：

1. **数据集创建（步骤4）**：用例告诉你要生成什么类型的项-每个用例在数据集中应该有代表性的项。
2. **评估者选择（步骤3）**：评估标准告诉您选择哪些评估者以及如何映射它们。

**从`pixie_qa/00-project-analysis.md`中的能力清单**中导出用例。**从困难的问题/故障模式中得出评估标准**，而不是像“真实性”或“相关性”这样的通用质量维度。

保持简洁——这是一个计划的产物，而不是一个全面的规范。

---

定义什么

# # # 1。用例列出应用程序处理的不同场景。从`pixie_qa/00-project-analysis.md`中的能力清单中获得这些——每个能力应该映射到至少一个用例。每个用例都成为数据集项的一个类别。**每个用例描述必须是简洁的一行代码，同时传达(a)输入是什么和(b)预期的行为或结果是什么。**描述应该足够具体，以便不熟悉应用的人能够理解场景及其成功标准。

如果可能的话，指出每个用例的预期难度级别——例如，对于简单的用例，“常规”，对于边缘用例或故障模式场景，“具有挑战性”。这将指导数据集创建（步骤4）包含一系列难度级别的条目，而不是在简单的情况下聚类。

**好的用例描述-“因查询帐户困难而转到人工代理”
-“使用客户CRM的计划详细信息回答计费问题”
-“拒绝回答支持领域以外的问题”
-“总结研究结果，包括所有查询的子主题”

糟糕的用例描述（太模糊）：**

-“处理帐单问题”
——“边缘情况”
-“错误处理”

# # # 2。Eval标准

定义高级的、特定于应用程序的评估标准——对这个应用程序至关重要的质量维度。每个标准将映射到步骤3中的评估器。

**好的标准是特定于应用程序的目的**和源自**困难的问题/故障模式**在`pixie_qa/00-project-analysis.md`。例子:-语音客服座席：“座席在转接前是否验证了呼叫者的身份？”，“电话应答是否足够简洁？”
-研究报告生成器：“报告是否涉及所有子问题？”，“所述主张是否得到检索来源的支持？”
- RAG聊天机器人：“答案是否基于检索到的上下文？”，“当上下文丢失时，它会说‘我不知道’吗？”
Web scraper：“提取的数据是否与请求的模式字段匹配？”，“它是否处理格式错误的HTML而不会崩溃或丢失数据？”**糟糕的标准是伪装成需求的通用评估器名称。**不要说“事实准确性”或“响应相关性”-说事实准确性或相关性对这个应用程序意味着什么。如果你的标准可以适用于任何聊天机器人（例如，“接地性”，“PromptRelevance”），他们太通用了-回到`00-project-analysis.md`的故障模式，并从中得出标准。

在这个阶段，不要选择评估器类或阈值。这是第三步。

# # # 3。检查标准的适用性和可观察性

对于每个标准：1. **确定适用范围** -此标准是否适用于所有用例，还是仅适用于一个子集？如果某个标准仅与某些场景相关（例如，“身份验证”仅适用于与帐户相关的请求，而不是一般常见问题解答），请清楚地标记它。这种区别对于第4步（数据集创建）至关重要，因为：
- **通用标准**→成为数据集级别的默认评估器
- **个案标准**→仅在相关行上成为项目级评估器

2. **验证可观察性** -对于每个标准，确定应用程序中需要捕获哪些数据点作为`wrap()`调用来评估它。这推动了步骤2中的包装覆盖率。
-如果标准是关于应用程序的最终响应→由`wrap(purpose="output", name="response")`捕获
-如果是关于路由决定→由`wrap(purpose="state", name="routing_decision")`捕获
-如果它是关于数据的应用程序获取和使用→捕获`wrap(purpose="input", name="...")`---具有多种功能的项目

如果项目分析（`pixie_qa/00-project-analysis.md`）列出了多个功能，您应该至少评估**2-3个最重要/最常用的**功能。当项目的价值来自于广度时，不要将数据集限制为单一功能。

对于第一个功能之外的每个附加功能：

-在`02-eval-criteria.md`中添加用例
-在步骤2中计划单独的跟踪（使用不同的入口点/配置运行`pixie trace`）
-在步骤4中规划涵盖该功能的数据集条目

如果时间或上下文的限制使涵盖所有功能变得不切实际，那么在`02-eval-criteria.md`的末尾**记录您涵盖了哪些功能，跳过了哪些功能**（有理由）。

##标准质量门（强制自检）

在写入`02-eval-criteria.md`之前，对每个条件运行以下检查：> **对于每个标准，问一问：“如果应用程序返回了一个结构正确但语义错误或幻觉的答案，这个标准会抓住它吗？”**

-如果所有条件的答案都是“否”，那么你的标准集是“仅结构”的-它检查管道（字段存在，数据流过），但不检查质量（内容正确，完整，无幻觉）。你必须添加至少一个语义标准来评估应用输出的内容，而不仅仅是它的形状。
-结构标准（字段存在，JSON有效性，格式检查）是有用的，但不够。即使应用程序返回伪造或错误的数据，它们也会通过。

结构标准和语义标准的例子

|结构（检查形状）|语义（检查质量）|| ------------------------------------------- | -------------------------------------------------------------------------- |
| “输出中存在必填字段” | “提取值与源内容匹配-无幻觉数据” |
|“源类型与预期类型匹配”|“应用程序正确地解释了嘈杂的输入而没有丢失关键事实”|
| “输出是有效的JSON” | “摘要准确地捕获了文档的要点” | "
“响应包含至少N个字符” | “响应针对用户的特定问题，而不是一般主题” | "

一个好的标准集既有结构标准又有语义标准。结构标准捕获严重故障（应用程序崩溃，返回空输出）。语义标准捕获质量故障（应用程序运行但返回wrong/hallucinated/incomplete内容）。
