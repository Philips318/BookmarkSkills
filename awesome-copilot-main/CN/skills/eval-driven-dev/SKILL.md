Python LLM应用程序的eval驱动开发

您正在构建一个端到端测试基于python的AI应用程序的自动化评估管道——以与真实用户相同的方式运行它，使用真实的输入——然后使用评估器对输出进行评分，并通过`pixie test`生成pass/fail结果。

你测试的是应用程序本身——它的请求处理、上下文组装（如何收集数据、构建提示、管理会话状态）、路由和响应格式。该应用程序使用LLM，这使得输出不确定-这就是为什么您使用评估器（LLM作为判断，相似性分数）而不是`assertEqual`-但测试的东西是应用程序的代码，而不是LLM。在评估过程中，应用程序自己的代码会真正运行——路由、提示汇编、LLM调用、响应格式——没有任何模拟或存根。但是，应用程序从外部来源（数据库、缓存、第三方api、语音流）读取的数据会通过仪器替换为测试指定的值。这意味着每个测试用例控制应用程序看到的数据，同时仍然执行完整的应用程序代码路径。

**规则：应用程序的LLM调用必须去一个真正的LLM。**不要用假实现替换、模拟、存根或拦截LLM。LLM是核心的价值生成组件——替换它会使eval同义重复（你同时控制输入和输出，所以分数是没有意义的）。如果项目的测试套件包含LLM模拟模式，那么这些模式是用于项目自己的单元测试的——不要将它们用于eval Runnable。**可交付的是一个运行真实分数的工作`pixie test`-不是一个计划，不只是仪器，不只是一个数据集。

这种技能是关于做工作，而不是描述工作。阅读代码，编辑文件，运行命令，生成工作管道。

首先，激活虚拟环境。为项目确定正确的虚拟环境并激活它。激活虚拟环境后，运行技能资源中包含的setup.sh。
该脚本将`eval-driven-dev`技能和`pixie-qa`python包更新为最新版本，如果pixie工作目录尚未初始化，则将其初始化，并在后台启动web服务器以显示用户更新。

**安装错误处理-你可以跳过什么与什么必须成功：**- **技能更新失败**→OK继续。现有的技能版本就足够了。
- **pixie-qa升级失败，但已经安装**→OK继续使用现有版本。
- **pixie-qa未安装，安装失败**→**停止。**向用户寻求帮助。没有`pixie`包，工作流无法继续。

步骤1：理解应用程序并定义eval标准

**首先，查看用户的具体要求提示。**在阅读应用代码之前，检查用户的要求：**引用的文档或规范**：提示是否提到要遵循的文件（例如，“遵循EVAL_SPEC.md中的规范”，“使用REQUIREMENTS.md中的方法”）？如果是这样，**先读取该文件** -它可能指定数据集，评估维度，通过标准或方法，覆盖您的默认值。
- **指定的数据集或数据源**：提示是否引用特定的数据文件（例如，“使用eval_inputs/research_questions.json中的问题”，“使用call_scenarios.json中的场景”）？如果是这样，请**读取这些文件** -您必须将它们用作eval数据集的基础，而不是制造通用的替代文件。
- **指定的评估维度**：提示是否列出要评估的特定质量方面（例如，“评估真实性、完整性和偏差”，“测试身份验证和工具调用正确性”）？如果是这样，那么在您的测试文件中，每个命名的维度都必须有一个相应的评估器。如果提示符指定了上述任何一项，则它们具有优先级。在继续之前阅读并整合它们。

步骤1有三个子步骤。每个都读取自己的引用文件并生成自己的输出文件。**在开始下一个子步骤之前，请完全完成每个子步骤

###步骤4：构建数据集

b> **参考**：现在阅读`references/4-build-dataset.md`以获取详细的子步骤。**目标**：创建将所有内容联系在一起的测试场景——可运行的（步骤2）、评估器（步骤3）和用例（步骤1c）。每个数据集条目定义了发送到应用程序的内容，应用程序应从外部服务中查看哪些数据，以及如何对结果进行评分。使用第2步中的引用跟踪作为数据形状和字段名称的真实来源。涵盖`pixie_qa/00-project-analysis.md`中**能力清单**中的条目，并包括针对在其中识别的**故障模式**的条目。**不要使用项目自己的测试装置、模拟服务器或示例数据作为数据集`eval_input`内容** -使用真实世界的数据代替。**应用程序中的每个`wrap(purpose="input")`必须在每个条目的`eval_input`中预先捕获内容** -当应用程序有输入包装时，不要让`eval_input`为空。b> **检查点**：在`pixie_qa/datasets/<name>.json`创建的数据集JSON，具有涵盖所有用例的不同条目。**数据集真实性审计通过** -条目使用具有代表性规模的真实数据，没有项目测试装置污染，至少有一个条目针对具有不确定结果的失败模式，并且每个`eval_input`都捕获了所有输入包装的内容。暂时不要阅读步骤5的说明。

###第五步：运行`pixie test`并修复机械问题

b> **参考**：现在阅读`references/5-run-tests.md`以获取详细的子步骤。**目标**：端到端执行完整的管道，并使其运行无机械错误。这一步严格地是关于修复精灵QA组件（数据集、可运行的、自定义评估器）中的设置和数据问题——而不是修复应用程序本身或评估结果质量。一旦`pixie test`没有错误地完成任务，并为每个条目生成真实的评估器分数，这一步就完成了。

b> **检查点**:`pixie test`运行到完成。每个数据集条目都有评估器分数（real`EvaluationResult`或`PendingEvaluation`）。没有设置错误，没有导入失败，没有数据验证错误。
>
如果测试出了错误，那就是QA组件中的机械错误——修复并重新运行。但是，一旦测试结果出来，就继续前进。不要在这里评估结果质量——这是第6步。**在测试结果出来后，请继续进行步骤6。**分析是必不可少的最后一步-没有它，待定的评估永远不会完成，用户得到未解释的原始分数，没有可操作的见解。不要停在这里，询问用户是否继续。

**迭代运行的循环规则**：每次成功的`pixie test`调用都会创建一个具体的`pixie_qa/results/<test_id>`目录，并开始一个新的分析循环。在编辑应用程序代码、提示符、数据集、求值器或重新运行`pixie test`之前，请为该结果目录完成步骤6。不要跳过早期的周期，只分析最后一次运行。

Web服务器管理

Pixie-qa在后台运行一个web服务器，用于向用户显示上下文、跟踪和eval结果。它由设置脚本自动启动（通过`pixie start`，它启动一个分离的后台进程并立即返回）。当用户完成了eval-driven-dev工作流时，告诉他们web服务器仍在运行，你可以使用：```bash
pixie stop
```
重要提示：web服务器停止后，web UI将无法访问。所以只有当用户确认他们已经完成了所有web UI功能时，才会停止服务器。如果他们想继续使用web UI，不要停止服务器。
