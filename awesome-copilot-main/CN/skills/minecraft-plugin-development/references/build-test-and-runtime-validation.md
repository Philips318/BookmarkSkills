#构建、测试和运行时验证

当Minecraft插件任务涉及构建配置、打包、生成资源、部署到本地测试服务器、可选插件集成、重新加载行为或发布准备时，使用此参考。

这对于带有许多YAML资源、阴影库、软依赖项（如PlaceholderAPI或MythicMobs）以及验证运行时配置的管理命令的Maven或Gradle Paper插件尤其有用。

构建元数据和生成的资源

插件项目通常将源资源保存在`src/main/resources`下，而构建工具将过滤后的输出复制到`target/classes`或`build/resources`中。

指导:—编辑源资源，而不是生成的副本。
-将`target/classes`，`build/classes`，`build/resources`和复制的服务器插件jar作为构建输出。
—当`plugin.yml`使用过滤值（如`${project.version}`）时，请确认在Maven或Gradle中启用了资源过滤。
保持`plugin.yml`、`name`、`main`、`api-version`、命令、权限、`depend`、`softdepend`和`libraries`与代码和构建文件保持一致。
-如果包或主类更改，在相同的更改中更新`plugin.yml`。
—如果命令名称发生变化，请同步更新命令注册、权限检查、选项卡补全和用法文本。

Maven形状识别：```xml
<resources>
  <resource>
    <directory>src/main/resources</directory>
    <filtering>true</filtering>
  </resource>
</resources>
```
着色和依赖范围

纸质插件通常结合了服务器提供的api、可选插件api和必须捆绑的库。

指导:

-保持`paper-api`， Bukkit， Spigot和可选插件api为`provided`，除非项目有明确的理由捆绑它们。
-服务器不提供的阴影库，如小型UI助手或独立实用程序库。
-当它们可能与其他插件冲突时，重新定位阴影库。
-禁用或审查依赖减少的POM输出，当它产生嘈杂或误导性的回购变更。
-不要屏蔽`depend`或`softdepend`中列出的插件api。
-如果`plugin.yml`使用Paper`libraries`，确保服务器版本支持该机制，并且依赖项应该由Paper加载而不是阴影。

常见的迁移示例：```xml
<relocation>
  <pattern>fr.mrmicky.fastboard</pattern>
  <shadedPattern>com.example.plugin.libs.fastboard</shadedPattern>
</relocation>
```
可选插件集成

与PlaceholderAPI、MythicMobs、worlddedit、经济插件、权限、NPC系统或自定义模型插件集成的插件应该在可选集成时清晰地降级。

指导:

-把需要的插件放在`depend`和可选的集成在`softdepend`。
-在注册引用可选插件事件类的监听器之前，检查`PluginManager#isPluginEnabled`。
将可选的集成代码隔离在侦听器、适配器或服务中。
-当一个软依赖缺失时记录一个明确的警告，游戏将会减少。
-确保可选的集成数据流通过插件的正常状态机，而不是绕过奖励，库存，任务，或清理逻辑。

对于mythicmobs风格的资源生物：-匹配稳定的内部暴徒名称，而不是显示名称。
-仔细解决玩家杀手，因为直接杀手可能是弹丸或其他实体。
-只有在插件接受奖励路径的所有权后才能清除原始掉落。
-保持自定义暴徒奖励与正常游戏奖励相同的清理和持久性逻辑。

运行时配置验证

配置繁重的插件受益于一个非破坏性的验证命令，该命令可以在启动、重新加载和测试轮之前运行。

有用的验证界面：-丢失的世界，大厅点，刷出点，区域，或试验室
-零半径或零体积区域
-优先级可能不明确的重叠区域
-未知perk， kit, objective, mob, tier, material，或侧边栏标识符
-被禁用的系统仍然被侧边栏线、奖励、目标或命令所引用
-冷却时间，奖励份额，以及超出安全范围的百分比总额

指导:

-返回警告和错误，而不是崩溃的每一个不完美的配置。
-缓存最新的验证结果，以便管理命令可以在重新加载后显示它。
—包括每个版本的配置文件和路径。
—刷新运行时服务前，请在重新加载后进行验证。
-保持自动修复保守；悄悄改变地图坐标、奖励或进程规则可能会让服务器操作员感到惊讶。

重新加载和服务刷新有状态插件重新加载是有风险的，但有时需要活动服务器迭代。

指导:

在重新构建使用它们的服务之前，重新加载类型配置模型。
—重新启动依赖于已更改的配置的重复任务。
重新加载后刷新在线玩家状态：区域，侧边栏，操作栏，NPC可见性，perk选择和活动目标状态。
避免在重新加载后堆叠重复的调度程序，boss条，全息图，npc或监听器。
-在拥有任务或派生实体的服务上首选显式的`stop()`和`start()`方法。
-如果重新加载只是部分支持，确切地说哪些系统需要服务器重启。

第一轮服务器测试计划

对于游戏玩法插件，当代码更改难以通过单元测试证明时，应包含一个简短的手动测试计划。

建议检查表:-启动已安装所需依赖项的目标Paper版本。
—确认插件加载没有控制台异常。
-如果插件有验证命令，则运行该插件的验证命令。
-测试核心命令和标签完成在播放器和控制台。
-测试加入，离开，死亡，重生，断开，重新连接，插件禁用清理。
-为更改后的功能测试一条快乐路径。
—测试一个失败路径，如缺少权限，冷却时间，无效的目标，缺少依赖，或错误的配置。
-确认生成的实体、生物、npc、全息图、记分牌、boss条和临时世界被清理干净。
-确认档案保存，奖励，排名更新，和UI刷新发生一次，并在预期的线程。

##检查清单

在完成构建或部署相关的更改之前，请验证：-源资源被更改，而不是生成输出
-生成的README或市场文件更新，如果存储库需要它
-构建文件和`plugin.yml`在版本、主类、依赖项和命令上一致
-阴影依赖关系在容易发生冲突时被重新定位
-可选的集成有保护和明确的降级行为
-验证命令或测试清单涵盖改变的游戏路径
-本地构建输出不会提交，除非存储库有意跟踪它
