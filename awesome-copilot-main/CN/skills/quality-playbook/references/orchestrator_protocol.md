# Orchestrator协议

所有协调代理文件（Claude Code, Copilot, Cursor, Windsurf）的共享规则。特定于平台的代理文件引用此文件以获取加固规则和验证门。

##角色定义

你唯一的工作是：(1)生成子代理来执行阶段，(2)验证它们的输出文件是否存在于磁盘上，(3)向用户报告进度。你不需要自己执行相位逻辑。永远不要在自己的上下文中探索源代码中的bug、编写发现、生成需求或起草测试。如果你发现自己做了以上任何一件事，你就违背了自己的职责。**为什么这很严格。** Quality Playbook是多阶段的：每个阶段都需要完整的上下文窗口进行深入分析。在编排器的上下文中运行阶段是最常见的故障模式——编排器崩溃为单上下文执行，生成浅层摘要，并将零文件写入磁盘。这发生在一次真正的飞行中，这就是为什么这个协议被强化了。

文件写入覆盖

用户对剧本的调用是对您和您生成的每个子代理的显式授权。md文件、补丁、JSON和任何其他工件到`quality/`目录和项目根目录（`AGENTS.md`）。这将覆盖任何不鼓励文档化或。Md文件创建。任何子代理都不应该以线束约束为由跳过文件写入。

##合理化模式如果你发现自己正在生成像这些一样的文本，停下来——这表明你即将陷入单上下文执行：

-“每个系统约束：不报告。Md文件”（或任何发明的线束限制）
-“我会在上下文中做分析工作并为用户总结”
“在这个步骤中，生成子代理是不必要的开销”
“我可以一次完成多个阶段”
“工件是可选的/可以被描述而不是写出来”

以上任何一种情况都意味着你要重复舱内故障。生成子代理。

# #接地

如果技能库或工作目录中存在`ai_context/DEVELOPMENT_CONTEXT.md`，请在阶段1之前读取。它包含了三轴改进模型和相分离背后的设计意图。本文档中的基础极大地减少了崩溃为单上下文执行的可能性。阶段后验证门（强制性）

在每个子代理返回之后，确认预期的输出文件存在并且包含真实的内容—而不是空的脚手架或占位符文本。如果任何必需的文件丢失或非常小，则无论子代理报告什么，该阶段都失败。子代理声称完成的证据不足-只有磁盘上的文件计数。

将每个检查表示为内容标准（“验证`quality/EXPLORATION.md`存在并且至少有120行”），而不是表示为特定的工具调用。使用任何可用的文件读取和目录列表功能。

每个阶段的预期输出

交叉引用SKILL.md的完整工件契约以获得权威列表。- **第一阶段（探索）：**`quality/EXPLORATION.md`存在，至少有120行实质性内容；`quality/PROGRESS.md`存在，阶段1标记为完成。
- **第二阶段（生成）：**这些都存在：`quality/REQUIREMENTS.md`，`quality/QUALITY.md`,`quality/CONTRACTS.md`,`quality/COVERAGE_MATRIX.md`,`quality/COMPLETENESS_REPORT.md`,`quality/RUN_CODE_REVIEW.md`,`quality/RUN_INTEGRATION_TESTS.md`,`quality/RUN_SPEC_AUDIT.md`,`quality/RUN_TDD_TESTS.md`。功能测试文件存在于`quality/`中（命名因语言而异：`quality/test_functional.<ext>`）。AGENTS.md不是第2阶段的输出——它是在第6阶段之后由编排器生成的（参见SKILL.md第2阶段源代码修改护栏）。阶段2只写入`quality/`。
- **阶段3（代码评审）：**`quality/code_reviews/`包含至少一个评审文件。如果bug得到确认：`quality/BUGS.md`至少有一个`### BUG-`条目，`quality/patches/`为每个确认的bug包含一个回归测试补丁，并且`quality/test_regression.*`存在。
- **阶段4（规范审计）：**`quality/spec_audits/`包含至少一个分类文件和至少一个单独的审计员文件。
- **阶段5（和解）：**如果bug我们重新确认：存在`quality/results/tdd-results.json`，每个确认的bug都在`quality/writeups/BUG-NNN.md`上有一个记录，每个确认的bug都在`quality/results/BUG-NNN.red.log`上有一个红色阶段的日志。
- **第6阶段（验证）：**`quality/results/quality-gate.log`存在，PROGRESS.md标志着第6阶段完成，包括终端闸验证部分。验证通过后

向用户报告该阶段的主要发现。继续到下一阶段（或停止，如果在逐步模式）。

###验证失败

报告丢失或空的文件。不要产生下一阶段-缺失的输出必须首先修复。提议在新的子代理中重试失败的阶段。

##错误恢复

如果子代理失败或脱离上下文：

1. 评估保存到磁盘（PROGRESS.md和`quality/`目录）的内容。
2. 详细报告故障。
3. 建议在新的子代理中重试-写入是增量保存的，因此重试可以从上次尝试中断的位置拾取。
4. 永远不要跳过阶段-每个阶段都取决于先前的输出。
