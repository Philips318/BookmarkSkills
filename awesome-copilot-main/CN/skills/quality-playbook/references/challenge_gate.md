#挑战门- Bug有效性审查

# #目的

挑战之门是一种自我对抗的审查，每个确认的bug必须在接受重写和回归测试之前存活下来。它可以捕捉到误报、过度分类的特征差距，以及模式匹配超越常识的发现。

门可以通过两种方式调用：

1. **在剧本运行期间** -自动应用于匹配触发模式的bug（见下文）。
2. **独立** -指向先前运行的`quality/`目录，以挑战特定的错误。例如:`"Read quality/writeups/BUG-042.md and the source code it references. Run the challenge gate on this bug."`两轮挑战

对于审查中的每个bug，正好运行两轮。每一轮都使用一个新的子代理，因此挑战者无需投入任何精力去寻找。

第一轮：“你觉得这是个真正的bug吗？”向代理提供：
bug记录（如果还没有记录，就写BUGS.md）
实际的源代码在引用的文件：行（阅读它新鲜-不要相信写的代码片段）
-引用位置上下10行以内的所有评论
-项目关于相关功能的README部分（如果有的话）

提示子代理：b>您正在审阅针对开源项目提交的错误报告。阅读下面的源代码和bug报告。然后回答：你觉得这是一个真正的bug吗？**
>
在分析任何事情之前，先运用常识。**从细节中退一步，问问自己：如果你把这段代码和这个bug报告给一个以前从未见过的高级开发人员看，他们会说“是的，这是一个bug”——还是说“这显然不是一个bug”？如果答案显然不是一个bug，立即说出来并解释原因。不要用一个常识性的答案来给自己找借口。这篇综述的目的是找出模式匹配凌驾于判断之上的发现。
>
b>然后考虑：
> -开发人员是否意识到这种行为？（查找注释、TODO标记、设计决策注释、WHY注释、OODA引用。）
> -这是记录在案的限制还是有意的权衡？(检查是否其他代码路径通过设计而不是偶然来处理这个问题。)
项目维护者会回答“这不是bug，这就是它的工作方式”或者“这是我们记录的已知限制”吗？
> - bug报告中的“预期行为”是任何规范所要求的吗，还是审计人员对代码应该做什么的意见？
> -这是开发脚手架吗？带有“change-me”、“placeholder”、“example”、“default”、“TODO”等名称的值并不是缺陷——它们是存在的自文档标记，使项目在开发过程中可构建。默认禁用并使用占位符值的特性是不完整的特性，而不是漏洞。
>
给出诚实的评价。如果真的有bug，就说出来并解释原因。如果不是，就说出来，并解释原因。即使代码可以改进，一个发现也可能“不是一个bug”——问题是这是否合理维护者会接受它作为缺陷报告。第二轮：有针对性的后续行动

基于第一轮的回答，生成一个针对性的后续问题。目标是对子代理在第一轮中所处的位置进行压力测试。

**如果第一轮说的是“真正的bug”：**后续应该从维护人员的角度挑战这个发现。在这个框架中使用一个新的子代理：b>你是这个项目的维护者。一个贡献者提交了这个bug报告。你编写了被批评的代码。阅读下面的代码、bug报告和第一轮评估。
>
写一个最令人信服的理由来说明为什么这不是一个bug。考虑：有意的设计决策、记录的限制、部署上下文、此language/framework中的常见模式，以及“预期行为”是否在任何权威的地方实际指定。
>
然后，在提出这个论点之后，说明你是否仍然相信它是一个真正的bug，或者这个论点是否让你相信它不是。

**如果第一轮说“不是bug”：**后续应该质疑解雇。在这个框架中使用一个新的子代理：>您是一名安全研究人员，正在审查此代码库。另一位评论者认为这个发现“不是bug”。阅读下面的代码、bug报告和第一轮解雇。
>
写一个最令人信服的理由，为什么这是一个真正的漏洞，尽管解雇。考虑：解雇没有处理的边缘情况，下游后果，当代码与其他组件交互时会发生什么，以及“故意”和“正确”是否相同。
>
然后，在提出这个论点之后，说明你认为这个发现应该被证实还是被驳回。

# # #判决

两轮比赛结束后，从三个裁判中选出一个：**确认** -两轮都认为这是一个真正的bug，或者第二轮的挑战未能破坏第一轮的确认。bug继续正常地进行编写和回归测试。
**降级** - bug是真实存在的，但是严重程度被夸大了。调整严重性并更新记录。常见情况：应该是MEDIUM的CRITICAL，或者实际上是代码质量问题的安全发现。
- **拒绝** -这个发现不是一个bug。它是一个有文档记录的设计选择、故意搭建、一个已知的限制、审计师的意见（而不是违反规范），或者常识认为明显不是缺陷的东西。删除bug ID。如果有用，将其记录在BUGS.md的“审查和驳回”附录中，并附上挑战推理。

给`quality/challenge/BUG-NNN-challenge.md`写判决书和两轮推理。该文件是审计跟踪-它向审阅者显示每个发现都经过了压力测试。自动触发模式

在剧本运行期间，自动将挑战门应用于匹配这些模式中的一个或多个的任何错误。这些模式是误报集中的地方：

|模式|触发|原因示例||---------|----------------|---------|
| **安全等级查找**（凭证泄漏，认证绕过，注入）|严重性校准自动升级这些；模型被激励去保护它们| BUG-041：“硬编码的JWT秘密”，这是一个开发占位符|
| **代码在引用的位置包含设计决策注释** | WHY注释，OODA引用，TODO-with-explanation或设计决策文档在引用的代码的10行内表明开发人员做出了有意识的选择|BUG-007/008:`// WHY-OODA81: Batch upload uses "default" workspace`|
| **“预期行为”没有规范基础** | Bug的spec_basis字段说“代码不一致”，而不是引用规范文档，或者需求是由审计员发明的（Tier 3 / REQ-NNN在运行期间创建）| Bug -041: REQ-019是由审计员创建的，而不是来自项目文档|
| **另一个代码路径处理相同的问题不同** |如果text_upload做X，但file_upload没有，那可能是一种真正的不一致——或者可能是有意的分歧。挑战在于找出是哪一个。|BUG-001/002: text_upload合并source_ids， file_upload覆盖-挑战确认这是一个真正的错误，因为text_upload有一个明确的修复注释|

##独立调用

当独立调用时（不是在剧本运行期间），挑战门：

1. 从`quality/writeups/BUG-NNN.md`读取指定的bug记录
2. 在引用的文件：行读取源代码（新读取，而不是从写入）
3. 如上所述运行两轮
4. 将裁决写入`quality/challenge/BUG-NNN-challenge.md`5. 如果判决被拒绝，建议从BUGS.md和tdd-results.json中删除bug

单独使用的示例提示符：```
Read the quality playbook skill at .github/skills/SKILL.md and .github/skills/references/challenge_gate.md.
Run the challenge gate on BUG-042 using the writeup at quality/writeups/BUG-042.md
and the source code in this repo.
```
## Token预算

每个bug大约需要2次子代理调用。对于具有5-10个自动触发bug的典型运行，则需要10-20个子代理调用。这比完整的迭代周期要便宜得多，并且可以捕获最高值的误报。

对于具有许多安全发现（bbb15自动触发）的运行，考虑批处理：首先对所有触发的错误运行第1轮，然后只对第1轮不明确或置信度较低的错误运行第2轮。
