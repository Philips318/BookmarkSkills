# #加密

静态加密

|数据灵敏度|最低标准||---|---|
|标准个人数据（姓名、地址、电子邮件）| AES-256disk/volume加密（云提供商默认）|
|敏感个人数据（健康、生物识别、金融、国民身份证）| AES-256 **列级**加密+通过KMS |进行信封加密
|加密密钥| hsm支持的KMS (Azure Key Vault Premium / AWS KMS CMK / GCP Cloud KMS) |

**信封加密模式：**
1. 使用**数据加密密钥(DEK)**加密数据（AES-256，每条记录或每个表生成）。
2. 使用存储在KMS中的密钥加密密钥（KEK）加密DEK。
3. 将加密的DEK与加密的数据一起存储。
4. 删除KEK =对所有用它加密的数据进行有效的加密分解。

传输中加密**必须**强制TLS 1.2最低；首选TLS 1.3。
- **必须**设置`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`。
- **绝对不能**允许TLS 1.0, TLS 1.1，空密码套件或出口级密码。
**绝对不能**在生产环境中使用自签名证书。

###密钥管理

-至少每年轮换DEKs；一旦怀疑有妥协，立即轮换。
—每个环境（dev / staging / prod）使用单独的密钥命名空间。
-记录所有KMS键访问事件-对异常访问模式发出警报。
-绝对不能在源代码或配置文件中硬编码加密密钥。

##密码哈希

|算法|参数|说明||---|---|---|
| **Argon2id**推荐|内存≥64mb，迭代≥3次，并行度≥4 | OWASP和NIST推荐|
| **bcrypt**可接受|成本因子≥12 |广泛支持；使用如果Argon2id不可用|
| **scrypt**可接受| N=32768, r=8, p=1 |备选|
| MD5 | - |永远不会损坏|
| SHA-1 / SHA-256 | - |绝不用于密码-不是为此目的设计的|

* *必须* *
-每个密码使用唯一的盐（内置于上述所有三种算法中）。
-只存储哈希-从来没有明文，从来没有可逆的编码。
-如果存储的哈希使用过时的算法，登录时重新哈希-透明升级。

* * * *
-添加一个胡椒（在哈希之前添加的服务器端秘密）存储在KMS中，而不是在DB中。
-在注册时根据已知的漏洞列表检查密码（`haveibeenpwned`API， k-匿名模式）。
—强制密码最小长度为12个字符。* *不能* *
-以任何形式记录密码-不是在注册期间，不是在登录失败期间。
—以url或查询字符串方式传输密码。
—以明文形式存储密码重置令牌-存储前进行散列。

##秘密管理

* *必须* *
-将所有秘密存储在专用的秘密管理器中：Azure密钥库，AWS秘密管理器，
GCP Secret Manager，或HashiCorp Vault。
-使用预提交钩子来防止秘密提交：`gitleaks`，`detect-secrets`， GitHub本地秘密扫描。
-立即轮换机密：开发人员离职，可疑的泄密，年度计划。
-保持一份机密清单文件-列出每个机密的用途和轮换日期。* * * *
-通过OIDC联盟（GitHub Actions→Azure/AWS/GCP）使用**短期凭证**代替长期API密钥。
-审核所有KMS机密访问-对工作时间以外或意外来源的访问发出警报。
—每个环境使用单独的秘密命名空间。

**`.gitignore`必须包含：**```
.env
.env.*
*.pem
*.key
*.pfx
*.p12
secrets/
appsettings.*.json   # if it may contain connection strings
```
* *不能* *
-将秘密提交到源代码存储库。
-将秘密作为纯文本CLI参数传递（它们出现在进程列表和shell历史记录中）。
-将秘密存储为代码中未加密的环境变量默认值。

匿名化和假名化

# # #定义

可逆的？| GDPR范围？用例||---|---|---|---|
| **匿名化** |否|不在GDPR范围内|删除后保留记录，分析数据集|
| **假名** |是（带密钥）|仍然是个人数据|分析管道，审计日志，降低风险处理|

匿名化技术

|如何|何时||---|---|---|
|抑制|完全移除字段|没有分析值|的字段
|屏蔽|用固定占位符（`"ANONYMIZED_USER"`）替换|删除后的审计日志标识|
|概化|用范围（年龄34→“30-40”）替换精确值|分析|
|噪声添加|为数值添加统计噪声|聚合分析|
|聚合|报告组统计信息，而不是单个值|报告|
| k-匿名|确保每条记录与其他k-1条记录无法区分|分析数据集|

假名化技术

|技巧|如何||---|---|
| HMAC-SHA256带秘钥|一致，单向，有密钥。用于分析中的用户id。输入KMS。|
|用不透明的令牌替换值；映射在单独的安全保险库中。|
|仅使用显式KMS授权进行解密。|

* *必须* *
-当删除用户时，**匿名**必须保留的记录（财务，审计日志）-用`"ANONYMIZED"`或散列占位符替换标识字段。
—将假名密钥存储在KMS中，不要与假名数据存储在同一个数据库中。
-使用断言测试匿名化例程：原始值绝对不能从输出中恢复。

**加密粉碎模式（事件源）：**
使用每个用户的DEK加密事件中的个人数据。将DEK存储在KMS中。
关于擦除：从KMS中删除DEK→该用户的所有事件都被有效地匿名化。* *不能* *
-如果可以通过与其他数据集的链接重新识别，则将数据称为“匿名化”。
—使用假名，并将映射键存储在与假名数据相同的表中。

##云和DevOps实践

* *必须* *
-为所有云存储启用静态加密：blob、托管数据库、队列、缓存。
-使用**私有端点** -数据库绝对不能公开访问。
—应用网络安全组/防火墙规则：仅在应用层限制访问数据库。
-启用云原生审计日志：Azure Monitor / AWS CloudTrail / GCP云审计日志。
-仅在**批准的地理区域**存储个人数据（EEA或充分性决定/ scc）。
-用`DataClassification`标签标记所有处理个人数据的云资源。* * * *
-启用Microsoft Defender for Cloud / AWS Security Hub / GCP SCC -每周审查建议。
-使用**托管身份** (Azure)或**IAM角色** (AWS/GCP)代替长期访问键。
—启用对象存储的软删除和版本控制。
—在云存储上应用DLP策略，检测PII写入未受保护的桶。
-为敏感表上的SELECT启用数据库级审计日志。

* *不能* *
—将个人数据存储在没有访问控制的公共存储桶中。
—生产端部署公网ip的数据库。
-如果数据可能溢出，则使用相同的云account/subscription用于生产和非生产。

---CI/CD控件* *必须* *
-运行**秘密扫描**在每次提交：`gitleaks`，`detect-secrets`， GitHub秘密扫描。
-运行**依赖漏洞扫描**每个构建：`npm audit`，`dotnet list package --vulnerable`,`trivy`,`snyk`。
请勿在CI测试工作中使用真实的个人数据。
-绝对不能在CI管道中记录环境变量-屏蔽所有秘密。

* * * *
在每个PR上运行**SAST**: SonarQube， Semgrep或CodeQL。
—执行命令**容器镜像扫描**:`trivy`、Snyk container或AWS ECR扫描。
-在管道中添加**GDPR合规门**：
-没有记录保留期的新迁移→失败。
—包含已知PII字段名的日志语句→warn。

**管道秘密规则：**```yaml
# MUST: mask secrets before use
- name: Mask secret
  run: echo "::add-mask::${{ secrets.MY_SECRET }}"

# MUST NOT: echo secrets to console
- run: echo "Key=$API_KEY"   # Never

# SHOULD: use OIDC federation (no long-lived keys)
- uses: azure/login@v1
  with:
    client-id: ${{ vars.AZURE_CLIENT_ID }}
    tenant-id: ${{ vars.AZURE_TENANT_ID }}
    subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
```

##事件和违规处理

监管时间表

|窗口|义务||---|---|
|通知监管机构（CNIL， APD, ICO…）-除非违规行为不太可能危及个人|
| **不得无故拖延** |通知受影响的数据主体，如果违规可能导致对其权利的**高风险** |

在内部记录所有的个人数据泄露——即使是那些不需要DPA通知的。

违约应对手册（模板）1. **检测** -定义标准：触发事件的因素（凭证泄漏、数据库转储暴露、勒索软件、意外的公共桶）。
2. **严重性分类** -根据数据的敏感性和容量分为低/中/高/紧急。
3. **遏制** -撤销泄露的凭据；隔离受影响的系统；保留证据（不要删除日志）。
4. **评估** -暴露了哪些数据？有多少科目？风险等级是什么？
5. **DPA通知** -使用监管机构的在线门户；包括：违规的性质、数据主体的类别和大致数量、记录的类别和大致数量、联络点、可能的后果、采取的措施。
6. **数据主体通知** -如果是高风险：明确的语言、违规性质、可能的后果、采取的措施、DPO联系方式。
7. **事件后回顾** -根本原因分析；纠正措施;向上runbook日期。###自动漏洞检测警报

为以下内容配置警报：
-异常的数据导出量（每小时阈值）
-在营业时间以外访问敏感表格
-批量删除事件
-认证尖峰失败
-出现在公共漏洞数据库中的新凭据（HaveIBeenPwned监控）

内部保存违规记录至少5年**。

架构模式

###数据存储分离
将操作数据（事务性DB）与分析数据（数据仓库）分离。
对每个应用不同的保留期和访问控制。
分析存储绝对不能直接从生产操作表中读取数据。

###专用同意存储
作为单独存储中的不可变事件日志跟踪同意，而不是用户表上的布尔列。
这使得：可审计的同意历史，版本跟踪，轻松撤销而不丢失数据。审计日志隔离
将审计日志存储在单独的、仅用于追加的存储中。
应用程序服务帐户绝对不能删除审计日志条目。
在审计表上使用具有仅插入权限的单独DB用户。

DSR队列模式
实现数据主体请求作为异步工作流：`POST /api/v1/me/erasure-request`→作业排队→工人擦洗所有存储→完成后通知用户。
这可以可靠地处理多存储清理的复杂性，并提供重试机制。

假名网关
对于分析管道，在两者之间的边界实现一个假名化服务
操作和分析系统。
映射密钥（HMAC密钥或令牌化库）永远不会离开操作区域。
分析区只接收假名标识符。Crypto-Shredding（事件源）
使用存储在KMS中的每个用户DEK加密事件中的个人数据。
对于用户擦除：删除DEK→该用户的所有历史事件都被有效地匿名化
不修改事件日志。
