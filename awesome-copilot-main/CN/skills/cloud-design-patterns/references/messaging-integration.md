#消息传递和集成模式

##编排模式

问题：中央编排器创建耦合和单点故障。

解决方案：让各个服务决定何时以及如何通过事件驱动的协作处理业务操作。

**何时使用**：
-松散耦合的微服务架构
-事件驱动系统
—避免中心业务流程瓶颈

* *注意事项* *实现:
-使用发布-订阅消息进行事件分发
—每个服务发布域事件并订阅相关事件
-实现复杂工作流的saga模式
-确保事件的幂等性，因为事件可能多次传递
-提供全面的日志记录和分布式跟踪

## Claim Check Pattern

**问题**：大消息可能压倒消息基础设施。**解决方案**：将大消息拆分为单独存储的声明检查（引用）和有效负载。

**何时使用**：
—消息超过消息系统大小限制
-减少消息总线负载
—异步处理大文件传输

* *注意事项* *实现:
-将负载存储在blob存储或数据库中
—通过消息总线只发送reference/URI—对存储的有效负载执行过期策略
—处理负载存储的访问控制
-考虑存储成本与消息传输成本

竞争的消费者模式

**问题**：单个消费者可能跟不上消息量。

解决方案**：允许多个并发消费者处理来自同一消息传递通道的消息。

**何时使用**：
—高消息吞吐量要求
—水平扩展消息处理
—跨多个实例的负载均衡* *注意事项* *实现:
-确保消息可以按任何顺序处理
-使用竞争的消费者队列（服务总线，RabbitMQ）
-实现消息处理程序的幂等性
-通过重试和死信策略处理有毒消息
—根据队列深度缩放消费者计数

消息传递桥模式

问题：不同的系统使用不兼容的消息传递技术。

解决方案：构建一个中介体，以支持不兼容的消息传递系统之间的通信。

**何时使用**：
—在消息传递系统之间迁移
-与遗留系统集成
-连接云和本地消息传递

* *注意事项* *实现:
—在系统之间转换消息格式
-处理协议差异
-如有需要，维护消息排序
—实现错误处理和重试逻辑
-监视桥的性能和运行状况管道和过滤器模式

问题：复杂的处理任务难以维护和重用。

解决方案**：将执行复杂处理的任务分解为一系列独立的、可重用的元素（过滤器），通过通道（管道）连接。

**何时使用**：
-处理具有多种转换的数据流
-构建可重用的处理组件
—支持独立操作的并行处理

* *注意事项* *实现:
—每个过滤器执行单个转换
—使用消息队列或流连接过滤器
-在可能的情况下启用并行执行
-在过滤器或管道级别处理错误
-支持过滤器组成和重新排序

发布者-订阅者模式

问题：应用程序需要向多个感兴趣的消费者广播信息。解决方案：允许应用程序异步地向多个消费者发布事件，而不耦合发送方和接收方。

**何时使用**：
-向多个相关方广播事件
-将事件生产者与消费者分离
-实现事件驱动架构

* *注意事项* *实现:
—使用基于主题或基于内容的订阅
—确保消息交付保证符合要求
—为选择性消费实现订阅过滤器
-在不影响出版商的情况下处理消费者故障
-考虑每个订阅者的消息排序要求

Scheduler Agent Supervisor模式

**问题**：分布式操作需要协调和监控。

**解决方案**：通过监控和管理工作流的主管协调一组跨分布式服务和资源的操作。**何时使用**：
-编排多步骤工作流
-协调分布式事务
—实现弹性长时间运行的流程

* *注意事项* *实现:
调度程序将任务分配给代理
—座席完成工作并报告状态
主管监控进度并处理故障
-实现失败步骤的补偿逻辑
—维护工作流恢复状态
