效率报告和后续审查

当用户询问发生了什么变化、需要before/after报告或要求再次传递剩余的昂贵作业时，加载此引用。

##报告规则

-将预期的节省与测量的节省分开。
-在没有before/after运行数据的情况下，不要声称节省了确切的时间或成本。
-调用混杂因素，如缓存预热，更改矩阵宽度，运行器更改，或异常小的pr。

当数据不完整时使用这个短语：`I can report the efficiency mechanisms that changed, but I cannot honestly claim exact minutes saved without comparing before/after GitHub Actions runs.`##测量什么

收集:

1. 更改前的基线样本
2. 缓存加热后的更改样例
3. 每个工作流或每个作业持续时间的比较
4. 避免跑步，跳过工作，或避免矩阵腿

总是分开:

- PR的挂钟时间
-跨作业的总运行时间
-完全避免工作它们回答了不同的问题。改变可以在不实质性改善最快反馈路径的情况下减少跑步者的花费。

##后续审查通过

在验证了第一轮修复后，检查剩余的昂贵作业：

-比较设置时间和执行时间
-识别重量级包装器动作并确认它们真正执行的内容
-检查每个矩阵维度是否仍然服务于主动决策
—缓存升温后重新检查
-在提出进一步的改变之前，打破主要的缓慢步骤

后续工作要紧凑。报告接下来几个最有价值的机会，而不是长长的愿望清单。
