#GitHub Actions仅当任务涉及GitHub Actions或CI工作流效率时才加载此引用。

如果回购是第一次导入GitHub Actions，首先定义一个最小的基线工作流，然后使用本指南的其余部分进行优化。

##审计命令

按此顺序检查：

1. 如果`.github/workflows/`缺失或为空，则首先收集基线需求：触发事件、所需检查、运行时版本和特定于存储库的验证策略。
2.`.github/workflows/*.yml`3. 描述CI期望的文档
4. 现有报告或运行历史记录（如果用户想要测量影响）

对于新的设置，从验证核心检查的小型工作流开始，然后仅在需要时添加矩阵宽度或额外的作业。

从常见的低风险浪费开始：1. 缺少依赖缓存
2. 缺少`concurrency`消去
3. 过于宽泛的工作流触发器
4. 跨文件或作业复制工作流覆盖
5. 无论范围如何，每次更改都会运行昂贵的作业

具体行动指导

触发作用域

-使用`paths`或`paths-ignore`，当整个工作流确实不应该运行某些文件类。
-当事件级过滤器太粗糙时，使用作业级门控。
-当可靠性比聪明的过滤器表达式更重要时，更倾向于显式的文件更改检测。

###工作塑造

—不要盲目合并作业。如果单独的作业可以保持并行性并缩短关键路径，那么就将它们分开。
-保持轻量级的协调或变更检测任务与繁重的执行任务分开，当这使得跳过行为明显时。
-如果一个仅工作流程的更改仍然运行完整的套件，将其视为闸门模型过于宽泛的证据。矩阵约简

将矩阵宽度与正在做出的决策相匹配：

-发布或显式兼容性验证的完整矩阵
-减少了运行时、插件、打包或框架集成更改的兼容性矩阵
-普通代码更改的单一代表性最新版本腿
-当已经存在较轻的保护时，对明显非运行时变化不进行重测试

###可选维护任务

格式化或自动修复回写分支的作业通常更适合作为可选作业。

好触发:

—PR标签，如`ci:format`-手动调度
-如果repo已经支持，则显式注释命令流

如果使用标签触发器，请记住监听PR`labeled`事件，通常是`unlabeled`事件，否则标签更改将不会重新评估作业。

##安全更改规则-不要隐藏所需的发布、迁移或共享库验证。
-当替换包装器动作时，不要意外地扩大更改文件范围。
-将严重性漂移视为回归风险。
-在用本地工具替换大动作之前，匹配实际检查面。

##实时验证

在可能的情况下，更喜欢实时GitHub验证：

—触发`workflow_dispatch`工作流一次
-通过两个快速更新验证过时运行取消
-在现有分支上使用增量的仅忽略或仅工作流程更改来验证路径控制
-在UI中确认重任务跳过，而不是假设它们会跳过

不要将新分支上的第一次推送视为干净路径忽略测试。
