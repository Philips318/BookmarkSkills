#企业入职

企业客户从签约到价值实现的四阶段框架。目标不仅仅是上线，而是持续的采用，而不是在第12周就崩溃。

##何时使用

* *触发:* *
-“我们如何加入这个企业客户？”
-“客户上线了，但采用率很低”
-“上线3个月后，我们的客户不断流失”
-“POC到生产的过渡”
“我如何防止第4周鬼影？”
-“客户成功入职框架”

* *背景:* *
-企业或中端市场交易
-复杂的技术要求
-涉及多个利益相关者
- 30-90天的实施时间表
-第一年的流失风险

---

核心框架

# # # 1。第四周的鬼影问题（以及如何预防）

* *的模式:* *第一周：开球电话进展顺利。每个人的兴奋。
第2-3周：技术发现，需求收集。还好。
第4周：客户停止响应。会议被取消了。“太忙了”。

* *发生了什么事?**

你在客户这边进行内部调整之前就开始了客户培训。

**谁拥有这个项目的内部？**
-销售代表？（已经开始下一笔交易了）
-技术冠军？（白天的工作取而代之）
-执行发起人？（代表，不开车）
——没人?（**这就是为什么他们会重影**）

框架：内部所有者验证

在开球前，回答：

**客户方谁将：**
-参加每周的项目会议？（没有“邀请”-实际上会出现）
-解锁procurement/legal/security的问题？(权威)
-推动最终用户的采用？(影响)
-当事情停滞时升级？（有行政权限）**如果你不能为每个项目指定一个具体的人，你就没有项目所有者。你签了合同，没人开车

**如何修复：**

**销售期间→CS交接（客户启动前）：**

销售代表必须确定：
-主要项目所有者（姓名，而不是角色）
-他们的能力（专业还是业余项目？）
-他们的权威（他们能解除封锁吗？）
-他们的动机（对他们有什么好处？）

**如果没有明确的所有者：**

先不要开始入职。让销售把你介绍给经济买家；

“在我们开始实施之前，我们要确保我们在您这边有合适的项目所有者。根据我们的经验，当有人每周都在推动这个过程时，实现就会成功。我们应该和你团队中的谁合作？”

* *常见的错误:* *

假设有人会拥有它。显式地问。如果他们不能说出某人的名字，这笔交易就有风险了。

---# # # 2。收养悬崖（第12周问题）

* *的模式:* *

上线发生在第6周。使用峰值。你庆祝。

第八周：使用趋于平稳。
第10周：使用率下降。
第12周：使用率较峰值下降50%。

**发生原因：**

你把上线当作终点线。“开始行动”是起跑线

**驱动持续采用的因素：**

**不是：**功能完整性，技术集成，培训课程

**是：**正在进行的价值演示，用户成功案例，扩展用例

**框架：上线后的采用阶段

**第1-6周（实施）：**让它工作
-测量：技术安装完成的百分比
-业主：技术主管

**第6-12周（初始采用）：**让人们使用它
-测量：#活跃用户，使用频率
-所有者：Enablement / DevRel**第12-26周（持续采用）：**证明持续价值
度量：用例扩展，团队扩展
-所有者：客户成功

**第26周+（扩展）：**在账户内成长
度量：新团队、新用例、升级触发器
-所有者：客户经理+ CS

**大多数球队错过的交接：**

第6周（上线）→第12周（持续采用）

大多数CS团队庆祝上线，然后转向下一个客户。**这是播种搅拌种子的时候

第6-12周：**

**第七周：**第一份价值报告
“以下是你的团队在第一周完成的任务：（具体指标）。这是第12周的情况：[目标]。”

第9周：**用户成功故事
“[用户名]在[团队名]上保存了[Xhours/reducedY错误]。他们是这样使用它的。”第11周：用例扩展对话
“你们在（主要用例）中使用我们。像你们这样的团队也使用我们来处理[相邻用例]。想要探索吗？”

* *常见的错误:* *

衡量“上线完成”，而不是“持续的活跃使用”。活下去不是成功。第26周的留存采用是成功的。

# # # 3。入职前：成功建立在第一个客户电话之前

* *的模式:* *

大多数入职失败都可以追溯到启动前的空白期。

**错过的：**

**销售没有正确地向CS介绍：**
-交易驱动因素未知
利益相关者动态不明确
-假定的技术要求

**没有确定的内部项目所有者：**
- CS伸出手，没人回应
-会议安排错了人
-决定不能坚持

**客户时间表不现实：**
-他们要在两周内上线
-技术设置至少需要6周
-从第一天开始期望就不一致**框架：启动前检查表**

在安排开球电话之前，验证：

* *账户情报:* *
-完成销售交接（交易驱动因素，利益相关者，技术要求）
-回顾过去的互动（演示笔记，提案，邮件）
-组织结构映射（团队规模，报告线）
[]记录用例（主要用例+未来用例）

内部设置:* * * *
-[]创建内部Slack通道（#account-[客户名称]）
-[]客户计划在CRM中更新
-[]已准备项目计划模板
-[]分配的角色（CSM主管，技术主管，执行主管）

* *客户准备:* *
[]项目负责人的名字（不只是“他们的DevRel团队”）
-[]双方确认执行赞助商
[]时间表的现实性（他们的目标和你的典型时间表）
-[]已知的阻碍文件（采购、安全、法律）* *时间验证:* *
-[]考虑到技术要求，客户的上线日期是现实的
-[]内部容量可用（未超售）
-[]识别依赖关系（SSO，集成，数据迁移）

* *决策标准:* *

只有当所有四个部分都通过验证时才安排开球。如果存在差距，在与客户接触之前，向销售或执行发起人说明。

* *常见的错误:* *

在内部不明确的情况下开始入职。这会造成混乱，错过最后期限，侵蚀客户信心。

# # # 4。四阶段入职流程

**第一阶段：开球（第一周）**

**目标：**与目标、时间线、成功指标保持一致

**参会者：**执行发起人+项目负责人+技术负责人* *议程:* *
1. 介绍和角色（5分钟）
2. 战略目标的执行一致性（5分钟）
3. 成功定义：“在3/6/12个月内，成功是什么样子的？”(10分钟)
4. 时间表和里程碑（5分钟）
5. 会议节奏（每周项目小组会议，每月高管会议）（5分钟）
6. 后续步骤（技术发现呼叫，成功计划回顾）（5分钟）

**可交付内容：**在24小时内发送启动概述，包括成功指标、时间表和后续会议

**第二阶段：发现与规划（第2-3周）**

**目标：**了解技术概况，绘制用例图，计划推出

**三个并行工作流：**

工作流程1：技术发现
-当前的基础设施（本地、云、混合）
-现有的工具和集成
-Security/compliance要求
-时间限制工作流程2：成功计划
-用例优先级（从最高价值开始）
-定义成功指标（如何衡量采用情况）
-确定培训需求（谁需要什么）

**工作流程3：技术设置**
—SSO/identity配置
-需要集成
-数据迁移（如适用）
-确定试点小组

**可交付：**客户成功计划文档，包括用例、指标、时间线、里程碑

**第三阶段：实施（第4-6周）**

目标：**部署到试验组，验证用例，为更广泛的推出做准备

**三个平行轨道：**

轨道1：管理和设置**
—SSO配置完成
-实时集成
-数据迁移（如适用）

曲目2：用户启用**
-试点小组培训课程
-文档共享
-办公时间安排Track 3: Pilot & Feedback**
-使用产品的试验组
-每周收集反馈
-问题分类和解决

**交付：**运行准备检查表完成，试验组验证

**阶段4：上线和持续成功（第6周以上）**

**目标：**广泛推出，维持采用，扩展用例

**第6-8周（上线）：**
-更广泛地推广到所有团队
-安排培训课程
-支持（Slack，电子邮件，办公时间）

**第8-12周（数值演示）：**
-首份价值报告（第7周）
-分享用户成功经验（第9周）
-用例扩展对话（第11周）

**第12-26周（持续收养）：**
-每月业务回顾
-采用跟踪（活跃用户、频率、用例）
-确定扩展机会

* *常见的错误:* *

将上线视为完成。第四阶段是决定留存率的阶段。

# # # 5。平行轨迹反模式* *的模式:* *

大多数入职团队按顺序运行工作流：
1. 技术设置（1-2周）
2. 然后训练（第3-4周）
3. 然后试驾（5-6周）

**总时间：6周**

**效果更好：平行轨道**

**同时进行技术设置、培训和试驾**；
-第一周：技术发现+确定试点小组+安排培训
—第2周：单点登录+飞行员组培训+飞行员开始
-第三周：整合+更广泛的培训+飞行员反馈

**总时间：3周**

**为什么并行工作：**

1. 缩短了价值
2. 保持客户参与（每周都会发生一些事情）
3. 及早发现阻碍因素（试点小组在广泛推广之前提出问题）

**如何执行：**

为每个轨道分配明确的所有者：
- Track 1 (Admin)：技术主管
-轨道2（启用）：Training/DevRellead
-赛道3（领航员）：CSM +领航员组冠军每周跨轨道同步以显示依赖项和阻塞项。

* *常见的错误:* *

等待“完美的技术设置”后开始试航。让试验组尽早使用它，即使设置不完美。他们的反馈使广泛的推广变得更好。

决策树

我应该开始客户入职吗？```
Has sales identified a project owner by name?
├─ No → Get project owner identified before kickoff
└─ Yes → Continue...
    │
    Is their timeline realistic given typical deployment?
    ├─ No → Reset expectations before kickoff
    └─ Yes → Continue...
        │
        Do you have internal capacity?
        ├─ No → Delay kickoff or get more resources
        └─ Yes → Proceed to kickoff
```
###这种入职方式有风险吗？```
Is customer responding to meeting invites?
├─ No → Week 4 ghosting, escalate to exec sponsor
└─ Yes → Continue...
    │
    Are they completing their action items?
    ├─ No → No project owner, identify who drives this
    └─ Yes → Continue...
        │
        Is pilot group using the product?
        ├─ No → Pilot group wrong or product not solving pain
        └─ Yes → On track
```
游戏上线后的采用是否持续？```
Are active users growing Week 6 → Week 12?
├─ Yes → Healthy adoption
└─ No → Continue...
    │
    Are active users declining?
    ├─ Yes → Adoption cliff, intervene immediately
    └─ No (plateau) → At risk, start value demonstration
```

常见错误

* * 1。在内部调整之前开始客户入职培训**
-浪费前2-3周，制造混乱，破坏信誉

* * 2。没有预先确定真正的项目所有者
-发现它第4周，必须重新启动或交易暂停

* * 3。在没有技术要求的情况下，在时间表上过度投入
-在执行过程中发现阻碍，错过了截止日期

* * 4。没有内部通信中心**
决策不会在团队中传播，会发生返工

* * 5。将投入使用视为项目完成**
-收养悬崖在第12周，账户有风险

* * 6。顺序轨道，而不是并行**
-实施时间延长一倍，客户失去动力

* * 7。上线后没有持续的指标
-发现领养问题为时已晚，无法保存帐户

##快速参考* * Pre-Kickoff验证:* *
-[]销售交接完成（交易驱动因素，利益相关者，需求）
-[]在客户端以姓名标明项目所有者
[]时间表现实（他们的目标和典型部署）
-[]内部角色分配（CSM，技术，执行发起人）

**开球议程（30-45分钟）：**
1. 介绍（5分钟）
2. 执行调整（5分钟）
3. 成功定义（10分钟）
4. 时间表和里程碑（5分钟）
5. 会议节奏（5分钟）
6. 后续步骤（5分钟）

**收养跟踪（第6-26周）：**
-第7周：第一份价值报告
-第9周：用户成功案例
-第11周：用例扩展对话
-第13周：第一次月度业务回顾
-第26周：扩展准备评估

四阶段:* * * *
1. 开球（第一周）：对齐
2. 发现（第2-3周）：计划
3. 实施（第4-6周）：部署到试点
4. 上线和持续（第6周以上）：推出、价值演示、扩展* *红旗:* *
-客户第4周没有回应→没有项目负责人
-试验组未使用第5周产品→错误的组或错误的用例
-活跃用户下降第8-12周→采用悬崖形成
