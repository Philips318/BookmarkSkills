#步骤6：按照回购惯例构建+测试

子代理类型：`task`（可以扇形分布到多个`explore`子代理）
平行表示发现)；预算：10分钟（延长上限为2倍）
缓慢的套房)。

# #输入

-步骤5中触及的文件集（来自每个修复子代理的）`files_touched`)。
-无论父节点从之前的回合中缓存了什么关于回购的信息
构建/测试/ lint命令集。

##返回合同```
{ status, failures }
```
其中`status`∈`pass`|`fail`和`failures`是相关的
从失败工具的输出中摘录(构建错误，测试失败，
Lint诊断)——足以让父进程决定是否循环
回到步骤5进行后续修复或按原样推送。

# #过程

**先发现** -阅读和组合：

——`.github/instructions/*.md`——`AGENTS.md`——`CONTRIBUTING.md`——`README.md`-`package.json`脚本，
——`Makefile`-特定于语言的工具配置；
-和最近的CI工作流程运行（`gh run list`,`gh run view`）学习
使用的*实际*命令集。

然后在修改后的代码上运行这些命令。独立的
发现轴（构建工具/测试运行器/ lint /拼写/格式）
可以作为单独的`explore`子代理并行调度；缓存
每轮发现的命令，所以重新运行不会重新发现。

# #陷阱- **不要发明通用的构建命令。**一个破碎的构建浪费了
下一个完整的复习周期（3-10分钟）。如果发现一无所获
表面的差距-不要猜测。
- **尊重仓库特定的拼写检查/ lint /格式策略
一些repos更喜欢重写而不是allowlist条目；有些人有patterns/regex文件;有些接受内联忽略指令。检查
在应用a之前，repo的现有配置和最近提交
通用的修复。
- **每轮缓存发现的命令，而不是每个循环。** Repo配置
可以在回合之间改变（一个修复可能会增加新的lint），所以重新发现
在每个回合的开始，但在回合内重用。
—**失败，路由返回步骤5。**当`status: fail`时，父级
将失败摘录作为新发现重新进入步骤5 -不要
推动一个破碎的构建来满足步骤7。
