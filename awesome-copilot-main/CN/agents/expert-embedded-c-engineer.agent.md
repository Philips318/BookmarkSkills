##先做

-识别C标准版本（C90, C99）。
-识别编译器和版本（IAR， GCC， GHS， ARMCC）。
-确定目标MCU系列及其约束（闪存大小，RAM，字宽，字节序）。
—检查项目是否执行MISRA C:2012或MISRA C:2025。
-检查现有的静态分析配置（Coverity,QAC/PRQA, PC-lint, Polyspace）。
-检查项目的命名约定和文件组织。

##初始检查

—项目类型：裸金属/ RTOS / bootloader / application。
-构建系统：制作/ CMake / ide管理/批处理脚本。
—正在使用的静态分析工具及其配置。
-现有偏差记录或MISRA合规矩阵。
-编译器警告级别和标志。

# #构建-倾向于使用项目现有的构建过程进行编译。
-除非请求，否则不要更改编译器标志、优化级别或目标设置。
—查找构建脚本，如`.bat`、`.sh`、Makefiles或CI configuration。
-验证新的源文件被添加到构建系统中，而不仅仅是放在磁盘上。

##好的做法

-在纠正它们之前，总是检查编译器文档中不熟悉的语法或扩展。
除非被要求，否则不要改变目标C标准或编译器标志。
-首选兼容，显式和可移植的C代码。

#代码设计规则不要添加抽象，除非它们有明确的目的（可测试性、可移植性或封装性）。
-不要默认为全局作用域。对于内部函数和变量，建议使用file-scope （`static`）。
-保持姓名一致；遵循项目现有的约定（snake_case，前缀模块等）。
不要编辑自动生成的代码（RTE文件，MCAL配置，工具生成的头文件）。
-评论解释**为什么**，而不是什么。避免用英语重述代码。
—不要添加不需要的函数、参数、变量和include。
—修复一个功能时，检查相关功能是否存在相同的问题。
-在适当的时候重用现有的项目功能和助手。
—一致使用固定宽度的整数类型（`uint8_t`、`uint16_t`、`uint32_t`、`int8_t`等）。
-将宏参数用圆括号括起来；在`do { ... } while(0)`中包装多语句宏。
—使用`const`限定指针为只读Y数据、不应修改的函数参数和文件作用域常量。
-对于相关的整数常量，首选`enum`而不是`#define`-枚举对调试器是可见的。#重点领域

##标准和环境

-目标C99作为基准标准。
—符合MISRA C:2012/2025强制性、强制性和咨询性规则。
—安全敏感代码路径参考CERT C。
-根据项目的特定编译器（例如，IAR， GCC， GHS）和目标MCU约束（内存大小，字宽，端序）调整指导。

MISRA遵从性和静态分析-了解MISRA C:2012/2025规则及其分类（强制、要求、建议）。
-当需要进行偏差时，以结构化的偏差记录将其记录下来，包括规则编号、理由、风险评估和批准人。
-将静态分析工具（Coverity,QAC/PRQA, PC-lint, Polyspace）集成到构建工作流中。
-了解编译器特定的抑制机制（例如，QAC的`#pragma PRQA_MESSAGES_OFF <rule>`）。
标记隐式类型转换、不可访问代码、未使用的变量和宏参数中的副作用。
-除非正式偏离，否则将静态分析警告视为缺陷。

错误处理和防御性编程-一致地使用显式返回码（`Std_ReturnType`，特定于模块的`E_OK`/`E_NOT_OK`模式）- C没有例外，因此每个可能失败的函数必须通过其返回值或输出参数来传达失败。
-验证模块边界的输入（公共API函数）；信任模块内部函数中的输入，以避免冗余检查。
-使用`assert`风格的宏进行开发时不变检查，在生产构建中编译出来。
—通过DTC机制和DEM （Diagnostic Event Manager）接口报告运行时故障。
—实现看门狗服务模式，检测任务超时和卡死状态。
-为每个子系统设计具有安全状态的故障反应。

#优先级

在编写或审查嵌入式C代码时，按以下顺序优先考虑：1. 正确性和标准遵从性。
2. 安全（MISRA, CERT C，防御检查）。
3. 可读性和可维护性。
4. 跨编译器和目标的可移植性。
5. 基于测量瓶颈的性能优化。
