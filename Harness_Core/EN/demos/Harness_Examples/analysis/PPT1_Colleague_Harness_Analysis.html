Executive Summary

它是什么：一台「自主执行引擎」What it is: an "autonomous execution engine"

一套在 VS Code + GitHub Copilot 中运行的自主 AI 开发流水线，把「需求→架构→计划(BDD)→开发→评估→演示→完成」编排为可长时间运行的 Agent 协作。An autonomous AI development pipeline in VS Code + GitHub Copilot that orchestrates "Requirements → Architecture → Plan (BDD) → Develop → Evaluate → Demo → Done" as long-running agent collaboration.

🎯 核心目标Core Goal

  • 用户一次调用 @orchestrator，系统自主实现整个特性
  • User invokes @orchestrator once; the system autonomously implements the whole feature
  • 只在 3 个人工 Gate 介入；任务 失败 3 次才需人工干预
  • Human intervenes at only 3 gates; manual help needed only if a task fails 3×
  • 面向 IEC 62304 医疗器械软件，内建 QMS 文档与多重质量门禁
  • Targets IEC 62304 medical-device software with built-in QMS docs and multi-gate quality control

🧬 理论根基Theoretical Basis

  • Anthropic「Effective Harnesses for Long-Running Agents」
  • Anthropic "Effective Harnesses for Long-Running Agents"
  • 生成器 + 评估器分离：Agent 无法客观评判自己的产出
  • Generator + evaluator separation: an agent can't objectively judge its own output
  • 上下文隔离是关键机制：测试设计者从不看生产代码
  • Context isolation is the key mechanism: the test-designer never sees production code

一句话定性：强调「自主、隔离、可评估」的执行机器，把 Agent 编排工程化到了可落地的成熟度。In one line: an execution machine emphasizing "autonomy, isolation, evaluability" — agent orchestration engineered to production-ready maturity.

Core Mechanism

关键机制：上下文隔离 + 生成/评估分离Key Mechanism: context isolation + generation/evaluation separation

① 上下文隔离Context isolation

每个 subagent 全新上下文。test-designer 从不看生产代码；evaluator/demonstrator 不共享 developer 记忆 → 诚实、无偏评估。Every subagent gets a fresh context. The test-designer never sees production code; evaluator/demonstrator don't share the developer's memory → honest, unbiased assessment.

② 生成 ≠ 评估Generation ≠ evaluation

开发与评估物理分离；evaluator 只跑测试、判质量、验证已存输出，自己不写测试。Development and evaluation are physically separated; the evaluator only runs tests, judges quality, verifies stored outputs — it authors no tests.

③ 结构化状态Structured state

.harness/ 是跨会话共享记忆：backlogs(JSON schema)、ADR、specs、eval_feedback、tool_outputs、progress。.harness/ is cross-session shared memory: backlogs (JSON schema), ADRs, specs, eval_feedback, tool_outputs, progress.

④ 单任务单会话One task per session

一次只做一个任务，防止上下文耗尽；orchestrator 独占任务状态标记。One task at a time prevents context exhaustion; only the orchestrator marks task status.

⑤ 先验证后构建Verify before building

动新代码前先确认基线为绿（Verify-Baseline.cmd）。Confirm the baseline is green (Verify-Baseline.cmd) before touching new code.

⑥ 定义变更只向下级联Definitions cascade down only

Gate 驳回/中途定义缺陷 → 回最高变更层，冻结已批上游，重走组合 Gate。Gate rejection / mid-flight definition gap → return to the highest changed layer, freeze approved upstream, re-run the combined gate.

Weaknesses / Gaps

🧩 领域/风险分析薄Thin on domain/risk analysis

缺 DFMEA、IFU、产品缺陷分析、影响分析等风险与临床文档能力；iec62304 仅覆盖流程合规。Lacks DFMEA, IFU, product-defect and impact analysis; iec62304 covers only process compliance.

🔧 缺「修复型」质量技能No "remediation" quality skills

只有 CI 端 TICS/Coverity 门禁，缺 Agent 侧 TICS/CodeScene 问题修复技能与 Philips 规则集。Only CI-side TICS/Coverity gates; no agent-side TICS/CodeScene fix skills or Philips rule sets.

🩺 无 CT/DICOM/光谱知识No CT/DICOM/Spectral knowledge

流程通用，但缺医疗影像专业知识库，难识别领域特有失效与安全红线。Process-generic but no medical-imaging knowledge base; hard to spot domain-specific failures and safety red lines.

Build 脚本 + Python venv + PDLM 模板 + .harness 状态，落地需较重环境搭建。Build scripts + Python venv + PDLM templates + .harness state require heavier setup.

To Strengthen

还需补充和加强的地方What to add & strengthen

  • 注入领域与风险层：引入 DFMEA / IFU / 影响分析 / 产品缺陷 / CT·DICOM·光谱知识库，让评估「懂医疗」。
  • Inject a domain & risk layer: DFMEA / IFU / impact / product-defect + CT·DICOM·Spectral knowledge so evaluation "understands medicine".
  • 质量从「门禁」到「修复」：补 tics-standard、codescene-health 类修复技能 + Philips 规则 instructions，Agent 能自愈而非只报错。
  • Quality from "gate" to "fix": add tics-standard / codescene-health remediation + Philips-rule instructions so agents self-heal, not just report.
  • 降低采纳门槛：提供最小可用配置 + 一键初始化；把 Build/Python 依赖做成可选分层。
  • Lower adoption cost: a minimal viable config + one-click init; make Build/Python deps an optional layer.
  • 技术栈解耦：把 Reqnroll/FlaUI 抽象为「测试策略」接口，允许替换。
  • Decouple the stack: abstract Reqnroll/FlaUI behind a "test-strategy" interface to allow substitution.
  • 补管理视角报告：为 evaluator/QMS 增加自包含 HTML 汇总（雷达图/热力图/追溯矩阵）。
  • Add management reports: self-contained HTML summaries for evaluator/QMS (radar/heatmap/traceability matrix).

Verdict

一句话评价Verdict in one line

Kunal 的 Harness 是一台成熟、诚实、可自主长跑的「执行引擎」——强在自主编排、上下文隔离与端到端测试/QMS 闭环；弱在领域深度、风险分析与质量自愈。Kunal's harness is a mature, honest, autonomously long-running "execution engine" — strong in orchestration, context isolation, and end-to-end test/QMS loops; weak in domain depth, risk analysis, and quality self-healing.

→ 它正好补上 Peng 方案「执行自动化」的短板；而 Peng 的领域/合规资产，正好补上它「懂医疗、能自愈」的短板。二者高度互补（见 Deck 2 / Deck 3）。→ It fills the "execution automation" gap in Peng's approach; and Peng's domain/compliance assets fill its "understand medicine, self-heal" gap. Highly complementary (see Deck 2 / Deck 3).
