AI Dev Harness — 端到端设计与门控指南

面向学习：讲清这个基于 @orchestrator 的自主流水线的设计、原理、门控，并以刚完成的 WW/WC-Reset 运行为实例。
Generator + Evaluator 上下文隔离 3 道人工门控 IEC 62304 CT 医疗软件
一段话：你只对 @orchestrator 提一个需求，它就驱动一条长时运行、基本自主的流水线 分析 → 规划 → 实现 → 独立评判 → 演示，只在三道人工门控处暂停。 它的核心是上下文隔离——评判工作的 agent（test-designer / evaluator / demonstrator）在 全新、独立的上下文中运行，看不到代码是怎么写的，所以判决可信。执行引擎之上叠加了 领域与合规层（CT/DICOM 知识、IEC 62304、DFMEA/IFU、TICS/CodeScene 自愈），提供"何为安全/正确/合规"。

1. 核心原则（可信性的来源）

#原则为什么重要
1上下文隔离是核心机制见过实现的 agent 无法客观测试/评判它；隔离才让判决可信。
2生成与评估分离作者与评判者永不为同一 agent/上下文。
3一次一任务；orchestrator 掌管状态只有它能标记任务完成，且须在门控 + CI 全过之后。
4动手前先验证基线改代码前确认 Build\Verify-Baseline.cmd 全绿。
5遵循 ADR；只碰新增/改动代码架构决策具约束力；规范只作用于新/改代码，不改造遗留。
6安全第一记录 IEC 62304 等级(A/B/C)+ 依据；患者数据路径或 Class C 一律升级。
7定义变更向下级联，绝不向上中途发现的缺口回到"最高被改层"，冻结已批准的上游，重新组合评审；定义缺口不消耗重试预算。
8双轨文档审计轨=活文档 QMS(md→docx)；管理轨=自包含 HTML 报告。
其他规则：每任务重试预算 max 3× 且共享；不编造 ID（RMM/需求 ID 保持 TBD/N/A）；被抑制/跳过的质量门 = 失败。

4. 门控详解（门控）

三道人工门控 + 一道自动质量门。人工门控是你做决定；自动门是隔离的评估者做决定。
⏸ GATE 1 — 组合评审（定义 what + how + plan）
时机：规划后、写码前。审查：需求(FR/NFR+安全等级)·架构(ADR)·backlog+Gherkin·风险。决策：Approve/Reject: 层——拒绝某层会向下级联（冻结已批准上游，重跑被改层及其下游，重新组合评审）。目的：花力气实现之前锁定定义。
⏸ GATE 2 — 设计 + 测试设计 评审（逐任务）
时机：@developer(DESIGN 模式) 与 @test-designer(TEST-DESIGN 模式)并行产出方案后、实现前。审查：实现设计说明(ADR 边界内) + 黑盒测试设计。目的：在写码前拦住错误方向，确认 test-designer 隔离完好。
🤖 自动质量门 — @dev-evaluator（隔离）
非人工门——全新上下文里的怀疑型评估者。做：跑全部测试(开发者单测/BDD + test-designer 黑盒)、评判测试质量(覆盖 + 断言强度)、核验开发者存档产物(存疑才重跑)、审查代码质量/架构遵从/功能完整/可演示性。判决：PASS/FAIL；FAIL 退回开发者并消耗一次共享重试。
⏸ GATE 3 — 功能演示（用户即裁判）
时机：@feature-demonstrator 启动应用、叙述功能并附视频/截图后。决策：用户批准/要求修改/拒绝；agent 不给通过/失败判决——人是裁判。目的：抓测试抓不到的——真实 UI 行为、工作流手感、集成实况。
重试预算：每任务 max 3× 且共享。定义缺口 ≠ 重试：若属定义问题(缺/错的需求、ADR、规格)，回到最高被改层且不消耗重试预算。orchestrator 掌管状态：只有它标记完成，且须门控 + CI 全过。

5. 为什么隔离是全部要点

@developer · 上下文 A
在 ADR 边界内实现；写生产代码。
@test-designer · 上下文 B
仅凭 feature 文件 + UI 契约编写黑盒测试；永不读生产代码——测试编码的是规格而非实现。
@dev-evaluator · 上下文 C
全新上下文中评判；不受开发者自辩影响；信任但核验存档产物。
领域/合规 skill 作为只读评判标准注入，不得破坏隔离（例如绝不把生产代码喂给 test-designer）。本次运行中，隔离的 test-designer 甚至产出了一个能自动拦截 demo bug 的回归测试。

10. 怎么自己跑

  1. VS Code + Copilot 打开仓库；确认基线全绿(Build\Verify-Baseline.cmd)。
  2. Copilot Chat 里用 @orchestrator 提出 feature/bug/改进需求。
  3. 在三道人工门控处答复(approve / reject-带理由)；拒绝会级联到最高被改层。
  4. 让它自主 实现 → 隔离评估 → 演示；仅当任务失败 3× 才需你介入。
  5. 一次性任务用 slash：/full-pipeline、/dfmea-analysis、/code-quality、/tics-preflight…
记忆模型：生成者 ≠ 评估者，且都在隔离上下文 → 判决可信。三道人工门控框住全程：定义(G1) → 设计(G2) → 演示(G3)，中间夹一道隔离评估客观门。.harness/ + progress.md 是持久大脑；Build/ + TICS/Coverity 是客观标尺。定义向下级联，绝不向上；orchestrator 掌管"完成"。

AI Dev Harness — End-to-End Design & Gates Guide

A learning primer for the @orchestrator-driven autonomous pipeline: its design, principles, and gates, with the just-completed WW/WC-Reset run as a worked example.
Generator + Evaluator Context isolation 3 human gates IEC 62304 CT medical software
In one paragraph: you give @orchestrator one request and it drives a long-running, mostly-autonomous pipeline — analyse → plan → build → independently judge → demonstrate — pausing only at three human gates. Its defining idea is context isolation: the agents that judge work (test-designer / evaluator / demonstrator) run in fresh, separate contexts and cannot see how the code was written, so their verdicts are honest. A domain & compliance layer (CT/DICOM knowledge, IEC 62304, DFMEA/IFU, TICS/CodeScene self-heal) supplies what "safe, correct, compliant" means.

1. Core principles (why it's trustworthy)

#PrincipleWhy it matters
1Context isolation is THE mechanismAn agent that saw the implementation can't objectively test/judge it; isolation makes the verdict trustworthy.
2Separate generation from evaluationAuthor and judge are never the same agent/context.
3One task per session; orchestrator owns statusOnly it marks a task complete, and only after gates + CI pass.
4Verify baseline before buildingConfirm Build\Verify-Baseline.cmd is green before changing code.
5Follow the ADR; new/changed code onlyArchitecture decisions are binding; conventions apply to new/changed code, not legacy retrofits.
6Safety firstRecord IEC 62304 class (A/B/C) + justification; patient-data path or Class C always escalates.
7Definitions cascade down, never upA mid-flight gap re-enters at the highest changed layer, freezes approved upstream; a definition gap does not consume the retry budget.
8Dual-track documentationAudit track = living QMS (md→docx); management track = self-contained HTML reports.
Also: retry budget max 3×, shared per task; no fabricated IDs (TBD/N/A until assigned); a suppressed/skipped quality gate = failure.

3. End-to-end pipeline (13 stages, 3 gates)

1 Analyse → 2 Req.review+Safety → 3 Architecture(ADR) → 4 Impact → 5 Plan(Backlog+Gherkin) | [ GATE 1 ] requirements + architecture + backlog + risk (combined review) | 6 Develop(BDD) =+ += parallel & isolated 7 Test-design =+ (black-box, spec only) | [ GATE 2 ] design + test-design review (per task) | 8 Evaluate(ISOLATED) → 9 Self-heal → 10 Risk/Compliance → 11 Docs → 12 Demonstrate | [ GATE 3 ] feature demo (user is the gate) | Done 13 Build & CI: TICS TQI>=8.0 & Coverity 0 new-High

4. The gates in depth

Three human gates + one automated quality gate. Human gates are where you decide; the automated gate is where an isolated evaluator decides.
GATE 1 — Combined review (define what + how + plan)
When: after planning, before any code. Reviews: requirements (FR/NFR + safety class) · architecture (ADR) · backlog + Gherkin · risk. Decision: Approve / Reject: <layer> — rejecting a layer cascades down (freeze approved upstream, re-run the changed layer + below, re-present the combined gate). Purpose: lock the definition before building.
GATE 2 — Design + test-design review (per task)
When: after @developer (DESIGN mode) and @test-designer (TEST-DESIGN mode) produce plans in parallel, before implementation. Reviews: the design note (within the ADR) and the black-box test design. Purpose: catch a wrong approach before code is written; confirm the test-designer's isolation.
🤖 Automated Quality Gate — @dev-evaluator (isolated)
Not a human gate — a skeptical evaluator in a fresh context. Does: runs ALL tests (dev unit/BDD + test-designer black-box), judges test quality (coverage + assert strength), verifies the developer's stored tool outputs (re-running only when in doubt), reviews code quality / architecture / completeness / demo readiness. Verdict: PASS/FAIL; a FAIL routes rework to the developer and consumes one shared retry.
GATE 3 — Feature demonstration (user is the gate)
When: after @feature-demonstrator launches the app and narrates it with video/screenshots. Decision: the user approves / requests changes / rejects — the agent gives no pass/fail. Purpose: catch what tests can't — real UI behavior, workflow feel, integration reality.
Retry budget: max 3×, shared per task. Definition gap ≠ retry: a definition problem re-enters at the highest changed layer and does not consume the budget. Orchestrator owns status: only it marks complete, only after gates + CI pass.

5. Why isolation is the whole point

@developer · context A
Implements within the ADR; writes production code.
@test-designer · context B
Authors black-box tests from feature files + UI contract only; never reads prod code — tests encode the spec, not the implementation.
@dev-evaluator · context C
Judges in a fresh context; can't be biased by the developer's rationalisations; trusts-but-verifies stored outputs.
Domain/compliance skills are injected as read-only judgment criteria and must not break isolation (never feed prod code to the test-designer). In our run, the isolated test-designer even produced a regression test that would auto-catch the demo bug.

10. How to run it yourself

  1. Open the repo in VS Code with Copilot; ensure the baseline is green (Build\Verify-Baseline.cmd).
  2. In Copilot Chat, invoke @orchestrator with a feature/bug/improvement request.
  3. Answer the 3 human gates (approve / reject-with-reason); rejections cascade to the highest changed layer.
  4. Let it implement → evaluate (isolated) → demonstrate autonomously; re-intervene only if a task fails 3×.
  5. For one-offs use slash prompts: /full-pipeline, /dfmea-analysis, /code-quality, /tics-preflight…
Mental model: generator ≠ evaluator, both isolated → honest verdicts. Three human gates frame the run: define (G1) → design (G2) → demonstrate (G3), with an isolated evaluator as the objective gate between. .harness/ + progress.md is the durable brain; Build/ + TICS/Coverity is the objective bar. Definitions cascade down, never up; the orchestrator owns "done."
